\section{Evaluation}
\label{sec:eval}

\subsection{Setup}

We evaluate \sys on an AWS cluster.
We spawn up to 70 nodes on \texttt{m5ad.2xlarge} instances with 8 vCPUs, 32 GiB memory, 300 GB NVMe SSD storage, and 10 Gbps network bandwidth.
They serve as the online machines (\autoref{sec:impl}) in the online performance benchmarks and as the offline machines in the checkpoint latency benchmarks, and they serve as both online and offline machines in the network traffic benchmarks.
We evaluate \sys and the compared systems operated by 4-100 nodes with these instances, where the faulty nodes keep silent to simulate availability attacks with maximum attacking power and no instance is assigned to them.
All the nodes are within the same availability zone.
For wide-area network experiments, we simulate network latency by applying artificial delays before sending outbound packets.
The latency values are taken from a public dataset~\cite{Reinheimer2020} of ping latencies between 247 cities worldwide.
We virtually place each replica node in a different, randomly-sampled city.
The average one-way latency between nodes is around 184ms, while the maximum one-way latency is over 400ms.

We spawn 20 \texttt{c5a.2xlarge} instances and run different numbers of concurrent close-loop client requests to generate workload.
We run each experiment for 30 seconds after a warm-up period of 10 seconds for LAN experiments and 20 seconds for WAN experiments, and we report the average throughput and medium latency during the measurement period.

We compare \sys with two other BFT systems: a fully-replicated BFT as baseline, and a sharded BFT system.
Both of the compared systems use the same Bullshark implementation as \sys as the atomic broadcast protocol.
For \sys and the fully-replicated BFT, we vary $f$ from 1 to 33, corresponding to 4 to 100 replicas.
For the sharded BFT system, we take the pre-determined fault tolerance cluster setting~\cite{ruan2021blockchains,el2019blockchaindb,hong2024gridb,amiri2021sharper,hellings2021byshard}, fixing $f=3$ in each shard and vary the number of shards from 2 to 10, which also maximizes at 100 replicas.
The sharded BFT system first orders the client requests via single unified atomic broadcast, then each fault tolerance cluster executes the requests assigned to it.
Thus, the consensus layer poses aligned performance and latency overhead on all compared systems, enabling fair comparison.
Despite the same consensus security, the sharded BFT system has significantly weaker tolerance to faulty replicas in the execution layer, because the clients only collect $f+1$ matching responses from the executing clusters instead of from all replicas.
We also implement the batched concurrent \fetch optimization described in \autoref{sec:overview} for the two compared systems.
While their \fetch operations can always be served by the local full copy of the state, the concurrent disk IO brought by the optimization still largely improves their performance.

We evaluate the systems with two applications: a key-value store and a UTXO-based cryptocurrency.
The state of the key-value store application follows conventional YCSB setting~\cite{cooper2010benchmarking}, containing 100 million key-value pairs, each with a 16-byte key and 1000-byte value of 10 fields, totaling around 100 GiB.
We evaluate the key-value store application with the YCSB benchmark workload B, with 95\% read and 5\% update operations.
The state of the UTXO application contains 100 million UTXO, each keyed with a 32-byte ID and a 4-byte index, and the values are 32-byte public keys and 8-byte amounts.
This is similar to the UTXO set size of Bitcoin as of present day, which contains around 173 million UTXOs~\cite{MempoolUTXOReport2025}.
The UTXO application is evaluated with simple transfer transactions.
Each client owns 1 UTXO in the initial state, and they repeatedly transfer that UTXO to new random addresses.
In the sharded BFT system, the input and output UTXOs may be managed by different clusters and thus require cross-shard communication.
We implement a client-coordinated two-phase commit protocol, closely following the previous practice~\cite{kokoris2018omniledger}.
For each transaction, the client submits it twice: in the first phase, the input clusters lock the input UTXO and respond signed messages to the client; in the second phase, the client submits the transaction along with the collected signed messages to both the input and output clusters to finalize the transaction.

The YCSB workload is extremely read-heavy: every operation, either read or update, involves a \fetch operation to read 1000 bytes of data.
On the other hand, the UTXO workload is write-heavy: each transfer transaction incurs one read and two writes, one to mark the input UTXO as spent and one to create a new UTXO.
In the sharded case, one read and one write land in the input shard, and the other write lands in the output shard.

\paragraph{Skewness and caching.}
Multiple studies~\cite{notallstate2025,krol2021shard,said2021detailed,kim2019ethanos,lin2025parallelevm} have confirmed that the access patterns of public blockchain states are extremely skewed.
\cite{kim2019ethanos} found that more than 95\% of the Ethereum accounts are inactive for more than a week from the respect of the current block.
\cite{krol2021shard} observed that in Ethereum, 20\% of the accounts contribute to 92\% of the transactions.
At state level, \cite{lin2025parallelevm} reported that the top 0.1\% state accounts for 62\% of all state accesses, while a recent report~\cite{notallstate2025} shows that 63.3\% of the Ethereum state is never accessed after setting.
As the result, caching is highly effective for blockchain execution.
BNB Smart Chain reports 90\% cache hit rate with their in-memory caching layer with just basic tuning and achieves 99\% cache hit rate with prefetching~\cite{nodereal2022_bsc_cache_hit_rate}.
In our YCSB workload, we simulate such skewed access patterns by setting a Zipfian distribution with a skewness factor of 1.24 for the accessed keys.
With this setting, the top 1\% most frequently accessed keys account for around 98\% of all accesses, and we simulate the cold or untouched majority state with 95\% keys which are accessed only around 1\% of the time.
We set the replica local cache size to 4 GiB and preload the cache with the 1 million (1\% of total) most frequently accessed keys before starting the experiments.
This skewness and caching combination results in around 90\% cache hit rate during the experiments.

\subsection{Storage Overhead}
\begin{figure}
    \includegraphics[width=\linewidth]{graphs/nodes-storage}
    \caption{The storage overhead of each node under various cluster sizes.
    }
    \label{fig:nodes-storage}
\end{figure}

In this experiment, we verify the storage scalability of \sys.
We prefill various numbers of nodes with the 100 million key-value pairs YCSB state and measure the storage overhead of the nodes, including both the online and offline machine.
Then we measure the size of database with \texttt{du} command, and the results are shown in \autoref{fig:nodes-storage}.
The fully-replicated BFT system shows no storage scalability: each node stores the full 100 GiB state regardless of the cluster size.
On the other hand, both \sys and the sharded BFT system show good storage scalability and the storage overhead of \sys is almost identical to that of the sharded BFT system.
With 100 nodes, each node of \sys only stores around 9.82 GiB data.
Because $r$ is set to 7, the full copies of each shard is stored by 7 nodes, and each node stores around $\frac{100\text{ GiB} \times 7}{100} = 7\text{ GiB}$ data in average.
The remaining storage overhead is due to the encoded chunks, whose redundancy ratio is around 3$\times$ and contributes around 3 GiB storage overhead per node.

This experiment confirms that \sys achieves the storage scalability goal: as more storage resources are added to the system by adding more nodes, the storage overhead of each node decreases accordingly and the system is capable of managing larger states.

\subsection{Performance Under Different Network Conditions}

\begin{figure}
    \includegraphics[width=\linewidth]{graphs/tput-latency}
    \caption{Throughput and latency of YCSB and UTXO applications under LAN and WAN network conditions.
    }
    \label{fig:tput-latency}
\end{figure}

We benchmark the performance is all three systems with 100 nodes, showing the throughput and latency results in \autoref{fig:tput-latency}.
\sys features consistent performance under both LAN and WAN network conditions.
Despite the extra network communication of SMS, the minimal latency of \sys is basically the same as that of the fully-replicated BFT system, around 670ms for LAN and 5.44s for WAN.
This is because SMS only incurs a single-trip latency overhead thanks to the pushing mechanism of primary nodes (\autoref{sec:impl}), which is negligible compared to the consensus latency dominated by Bullshark.

On the throughput side, \sys consistently outperforms the fully-replicated BFT system in both applications and network conditions.
Unintuitively, the state access overhead of \sys is \emph{lower} than that of the fully-replicated BFT system despite the remote accesses.
For YCSB workload, most of the \fetch operations are served by the local cache in both systems, so the performance difference is minor.
Although \sys nodes need to issue retrieval RPCs through the network for cache misses, they also save the local disk accesses, which could be even more expensive than the network transmission and lightweight verification of remote retrievals.
And for the write-heavy UTXO workload, the online machines of \sys incurs a trival \bump overhead to mutate the update table and stream the updates to the offline machines, while the nodes in the fully-replicated BFT system need to maintain their own full copy of the state and pass the updates to RocksDB.
As the result, \sys achieves around 2.6$\times$ throughput of the fully-replicated BFT system in the UTXO workload.

The sharded BFT system achieves the highest throughput in all cases, because each fault tolerance cluster only manages a fraction of the state and processes a fraction of the requests.
However, because the consensus overhead is aligned among all systems and the workload is skewed, the performance gap for YCSB workload is only around 2.24$\times$.
For the UTXO workload, while the workload is not skewed, the cross-shard communication overhead and two-phase commit protocol puts even more pressure on the performance of the sharded BFT system, resulting in a even smaller performance gap of around 1.5$\times$.
