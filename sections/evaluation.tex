\section{Evaluation}
\label{sec:eval}

\subsection{Setup}

We evaluate our system on an AWS cluster.
We run up to 70 replica nodes on \texttt{m5ad.2xlarge} instances with 8 vCPUs, 32 GiB memory, 200 GiB NVMe SSD storage, and 10 Gbps network bandwidth.
In all experiments, $f$ replicas keep silent to simulate availability attacks with maximum attacking power.
We run 20 \texttt{c5a.2xlarge} instances as clients to generate workload.
All the nodes are within the same availability zone.
For wide-area network experiments, we simulate network latency by applying artificial delays before sending outbound packets.
The latency values are taken from a public dataset~\cite{Reinheimer2020} of ping latencies between 247 cities worldwide.
We virtually place each replica node in a different, randomly-sampled city.
The average one-way latency between nodes is around 184ms, while the maximum one-way latency is over 400ms.

We compare \sys with two other BFT systems: a fully-replicated BFT as baseline, and a sharded BFT system.
Both of the compared systems use the same Bullshark implementation as \sys as the atomic broadcast protocol.
For \sys and the fully-replicated BFT, we vary $f$ from 1 to 33, corresponding to 4 to 100 replicas.
For the sharded BFT system, we take the pre-determined fault tolerance cluster setting~\cite{ruan2021blockchains,el2019blockchaindb,hong2024gridb,amiri2021sharper,hellings2021byshard}, fixing $f=3$ in each shard and vary the number of shards from 2 to 10, which also maximizes at 100 replicas.
While the sharded BFT system can tolerate up to 30 faulty nodes in total in this setting which is close to \sys and the fully-replicated BFT, this is a significantly weaker fault tolerance guarantee since the system is vulnerable to any faulty pattern that concentrates more than 3 faulty nodes in any single shard.
We also implement the concurrent \fetch optimization described in \autoref{sec:overview} for the two compared systems.
While their \fetch operations can always be served by the local full copy of the state, the concurrent disk IO brought by the optimization still largely improves their performance.

We evaluate the systems with two applications: a key-value store and a UTXO-based cryptocurrency.
The state of the key-value store application contains 1 billion key-value pairs, each with a 16-byte key and 84-byte value, totaling around 100 GiB.
The state of the UTXO application contains 100 million UTXO, each keyed with a 32-byte ID and a 4-byte index, and the values are 32-byte public keys and 8-byte amounts.
This is similar to the UTXO set size of Bitcoin as of present day, which contains around 173 million UTXOs~\cite{MempoolUTXOReport2025}.

We evaluate the performance of the systems with close-loop workloads generated by different numbers of concurrent clients.
We evaluate the key-value store application with the YCSB benchmark~\cite{cooper2010benchmarking} workload B, with 95\% read and 5\% update operations.
The UTXO application is evaluated with simple transfer transactions that transfer a random UTXO to a random recipient.
The two workloads have distinct characteristics: the YCSB workload is non-transactional read-heavy, while the UTXO workload is transactional and write-heavy.
For the sharded BFT system, we evenly partition the key space for the key-value store and the UTXO ID space for the UTXO application across all shards.
For the YCSB workload, client send requests to the corresponding shard based on the key.
For the UTXO workload, we implement a simple client-coordinated two-phase commit protocol to support cross-shard transactions, closely following the previous practice~\cite{kokoris2018omniledger}.

Without further notice, we run each experiment for 30 seconds after a 10-second warm-up period and report the average throughput and p99 latency during the measurement period.
