\section{Related Works}
\label{sec:rel}

\paragraph{Sharded blockchains.}
SharPer~\cite{amiri2021sharper}, ByShard~\cite{hellings2021byshard}, GriDB~\cite{hong2024gridb} and BlockchainDB~\cite{el2019blockchaindb} are sharded blockchains with a similar security model to \sys.
They propose to deploy multiple consensus instances on different sets of nodes, each tolerating up to $f$ Byzantine faults.
Other sharded blockchains, such as Omniledger~\cite{kokoris2018omniledger}, RapidChain~\cite{zamani2018rapidchain}, and Dang et al.~\cite{dang2019towards}, adopt a different security model where the systems tolerate a certain fraction of Byzantine nodes across the entire system, and the node shards are formed via random sampling at runtime.
As discussed in \cref{sec:review}, both categories of sharded blockchains suffer from performance degradation due to cross-shard transactions.
Basil~\cite{suri2021basil} discussed more shortcomings of sharded blockchains in detail.

\paragraph{BFT scalability.}
Many works have focused on scaling BFT consensus protocols, including SBFT~\cite{gueta2019sbft}, HotStuff~\cite{hotstuff}, Tusk~\cite{narwhal}, Bullshark~\cite{bullshark}, Autobahn~\cite{giridharan2024autobahn}, and Mysticeti~\cite{mysticeti}.
Some of them also adopt sharding techniques, such as Elastico~\cite{luu2016secure} and OHIE~\cite{yu2020ohie}.
While these works significantly improve the scalability of BFT consensus, the transaction execution is still sequential and fully replicated, becoming the bottleneck of the system.

\paragraph{Ordering, commutativity, and determinism.}
In fail-stop replication, EPaxos~\cite{epaxos} and CURP~\cite{curp} deliberately leave commutative operations unordered, since consensus dominates the cost there and bypassing it saves round trips.
\sys takes the opposite position, because both sides of that tradeoff invert under Byzantine faults.
Ordering has become cheap: DAG-based BFT protocols~\cite{narwhal,bullshark,mysticeti,giridharan2024autobahn} sustain a total order whose throughput grows with the number of nodes.
Forgoing it, in contrast, has become expensive, as concurrency control must then remain correct against arbitrarily misbehaving clients, which is what drives Basil to a $5f+1$ replication factor, per-transaction signatures, and performance that degrades once Byzantine behavior appears.
We therefore treat a total order not as an obstacle to parallelism but as an enabler of it, in the spirit of deterministic databases~\cite{calvin,aria}, which fix a transaction order up front so that partitions can execute against it independently and still converge.
\sys uses BFT consensus as precisely such a deterministic concurrency control policy: every correct node derives the identical state access sequence from the ordered blocks, so the state shards can be accessed concurrently with no coordination and no risk of divergence.

\paragraph{Blockchain execution engines.}
LVMT~\cite{li2024lvmt}, COLE~\cite{zhang2024cole}, Block-STM~\cite{gelashvili2022blockstm} and ParallelEVM~\cite{lin2025parallelevm} improve the performance of blockchain execution engines by optimize IO efficiency and parallelizing execution.
They improve the performance of individual nodes and can be used together with \sys as scalably performant BFT systems.
