\paragraph{Problem Settings.}
Our work functions as a replicated service for arbitrary state machines~\cite{lamport1978implementation} exhibiting tolerance to Byzantine faults akin to conventional BFT protocols.
The main focus is on the space consumed on participating nodes for storing the \emph{state}, the data component manipulated by the replicated state machine.
Specifically, \sys ensures both
\begin{description}
    \item[Security]
    \sys ensures safety and liveness properties consistent with conventional BFT protocols~\cite{pbft} with standard settings.
    \item[Storage scalability]
    The storage consumption on each node is proportional to the state size and inversely proportional to the number of nodes.
    In contrary, state storage in traditional BFT remains the same regardless of the system size.
\end{description}
\sys operates with $3f+1$ nodes and guarantees the aforementioned properties when up to $f$ nodes exhibit Byzantine faults and behave arbitrarily.
Following numerous prior studies~\cite{pbft,gueta2019sbft,yin2019hotstuff,danezis2022narwhal,spiegelman2022bullshark,luu2016secure,kokoris2018omniledger,dang2019towards,amiri2021sharper,gupta2020resilientdb,wang2019monoxide}, \sys achieves these properties under a partially synchronous network model.
Outside the period of synchrony, the protocol may experience a lack of progress, but safety and storage scalability remain uncompromised.

The rapidly expanding state sizes of prevalent permissionless blockchains are a well-established phenomenon.

\paragraph{The Necessity of Storage Scalability.}
The permissionless blockchains consist of decentralized nodes with heterogeneous storage capacities.
While the state sizes rapidly increase, more and more nodes cannot afford the storage costs and are forced to drop out.
This leads to a gradual centralization of the network, as only nodes with sufficient resources can continue to participate.
At the same time, the nodes with abundant storage resources are not able to utilize their extra storage to benefit the system.
\sys, on the other hand, features storage scalability, allowing the nodes to effectively \emph{lend} their extra storage to the system by, e.g., joining the network with multiple virtual nodes.
The increased total number of nodes can effectively alleviate the storage pressure on every node, enabling nodes with limited storage capacity to continue participating in the system.
At the same time, by spawning more virtual nodes, the nodes with abundant storage resources can be further incentivized for contributing more storage to the system.

In the permissioned settings, it may seem like the storage overhead is less concerning than in permissionless settings due to the more abundant resources normally found in the deployed environments.
However, because of the static and known membership, these systems cannot replace the participating nodes as easily.
Without storage scalability, the system would require every node to store the entire state.
The system must be halted if any \emph{single} node does not meet the storage requirements.
As more nodes join the network and more data is ingested, the early participants may be overwhelmed.
On the other hand, storage scalability can maintain a constant storage requirement on these nodes when the data brought by the new participants is proportional to the number of them.

\paragraph{Blockchain Systems with Scalable Storage (\autoref{tab:compare}).}
Prior works have proposed various blockchains with low storage overhead~\cite{ruan2021blockchains,el2019blockchaindb,hong2024gridb,kokoris2018omniledger,dang2019towards,zamani2018rapidchain,david2022gearbox,amiri2021sharper,gupta2020resilientdb,wang2019monoxide}.
They can be categorized into two main approaches: \emph{processing sharding} and \emph{stateless blockchain}.
Next, we introduce both approaches in detail and discuss their limitations.

\gd{Cite~\cite{luu2016secure} in related work as sharded but not storage scalable.}

The processing sharding approach horizontally partitions the state into multiple \emph{shards} and assigns each shard to a subset of nodes, called \emph{committees}\footnote{
    In this line of works \emph{shards} usually refer to the committees, or the \emph{node shards}.
    In this work, we follow the distributed database terminology and use \emph{shard} to refer \emph{data shards}.
}.
Every transaction is processed only by the committee(s) that manages the relevant shard(s).
One important insight is that the committees consist of fixed number of nodes.
As the number of nodes increases, the number of committees also increases, and the state size managed by each committee decreases proportionally, achieving storage scalability.

Based on this approach, \cite{ruan2021blockchains,el2019blockchaindb,hong2024gridb,amiri2021sharper,hellings2021byshard} leverages \emph{fault-tolerant clusters} as the natural committees.
\cite{kokoris2018omniledger,dang2019towards,zamani2018rapidchain,wang2019monoxide} instead design sophisticated \emph{committee formation} protocols to dynamically form committees that are secure with high probability.

The stateless blockchains~\cite{xu2021slimchain,boneh2019batching,chepurnoy2018edrax,tomescu2020aggregatable,xu2022l2chain} \emph{outsource} the state to external storage nodes.
The storage nodes submit the blocks to the consensus nodes along with the execution results and the proofs that show the correctness of the execution.
The consensus nodes can \emph{attest} the execution results before reaching agreement on them.

\begin{outline}
Currently, two approaches can achieve storage scalability.
\emph{Process sharding} process each transaction, i.e., reach consensus and execute the transaction, with a subset of the nodes.
The nodes only need to store the state that is relevant to the transactions they process.
\emph{Stateless blockchain} store the states on dedicated \emph{storage nodes}, who may only store part of the state and execute the transactions supported by the stored part.
While the consensus nodes need to reach consensus for all transactions, they are not required to store any state, as they can validate the execution results from the storage nodes \emph{statelessly} through verifiable computation or authenticated data structures.
While the original works propose to deploy storage nodes on dedicated devices, complicating the security model, they are also compatible to colocate the storage nodes with the consensus nodes.

Scaling out blockchain state has been the recurring topic of blockchain databases.
As the blockchain databases keep operating, the size of content they store may ever grow.
However, blockchains, as state machine replication protocols, by default require each node to store a full copy of the state in order to replicate the execution individually.
Eventually, the ever-growing database will overwhelm the storage capacity of the nodes.
Some blockchain databases leverage the inherent structure of rational databases and decompose the databases into table-level sub-chains~\cite{el2019blockchaindb}.
The researches go further by utilizing authenticated data structures~\cite{martel2004general, tamassia2003authenticated} to safely process cross table queries (\eg join operations)~\cite{zhang2015integridb,hong2024gridb}.
However, more universal solutions that are compatible with single large table or even agnostic to state structure are demanded for more widely adoption.

\paragraph{Sharded blockchains}
One layer down, the blockchains can divide the stored data into shards\cite{corbett2013spanner} and each node stores only one or a subset of the shards.
However, without the whole state, the nodes can no longer process every transaction.
EIP-4844~\cite{eip4844} of Ethereum bypasses this limitation by sharding \emph{blob}, a special kind of block data only whose (succinct) commitment is fully replicated and accessible by the transactions.
This approach is not desirable by blockchain databases which requires the whole data to present in the state.

Currently, the sharded blockchain works perform \emph{processing sharding} like regular distributed databases -- each node processes a subset of the transactions that only make use of the state shard(s) it stores.
The immediate effect of a reduced processing quorum is low fault resiliency (unless when reaching out for synchronous BFT protocols~\cite{zamani2018rapidchain}), \eg, tolerating $\frac{1}{4}$ faulty nodes globally~\cite{luu2016secure,kokoris2018omniledger,eyal2016bitcoin,dang2019towards} or $\frac{1}{3}$ faulty nodes locally within each processing quorum~\cite{el2019blockchaindb,amiri2021sharper}.
