\section{Motivation}
\label{sec:bg}

\paragraph{Problem settings.}
In this work we target the BFT replications protocols that perform state machine replication (SMR) over states that potentially cannot fit into single node's storage.
We don't assume any specific structure of the state, only requires it to be compatible for \emph{sharding}~\cite{corbett2013spanner}.
The number of shards is also not significant, though sufficient shards (\ie much more than the number of nodes) can achieve a better load balance effect.
Examples of compatible states are key-value stores (atop what relational databases potentially build)~\cite{corbett2013spanner} and (Merkle) Patricia Trie used by Ethereum.

We also do not assume any specific structure of the transactions, which may range from simple key-value updates to complex smart contracts.
We only expect that most transactions in the workload access only single or few shards (\ie online transaction processing (OLTP) workload instead of online analytical processing (OLAP)).
This expectation is valid for extensive scenarios such as token transfer between a pair of accounts or status update of a specific merchandise in a supply chain.
Besides, OLAP workload that scans over large number of shards can be performed off-chain with a verified state snapshot.

Note that because of the correspondence of replicating log and state established by SMR, several works focus on the availability of a sharded log (\ie the blocks in blockchains)~\cite{qi2020bft,eip4844}.
While the intermediate state can always be reconstructed with an available chain of blocks, blockchain databases demand \emph{explicit} states for online execution of transactions.
To keep a bounded storage usage, \sys releases historical blocks that will not be required by any further execution.

As the blockchain databases keep operating, the size of content they store may ever grow.
However, blockchains, as state machine replication protocols, by default require each node to store a full copy of the state in order to replicate the execution individually.
Eventually, the ever-growing database will overwhelm the storage capacity of the nodes. 

\paragraph{Sharded blockchains.}
To overcome this problem, the stored data can be divided into shards and each node stores only one or a subset of the shards.
However, without the whole state, the nodes can no longer process every transaction.
One line of works shard the historical ledger (\ie the blocks) and leave the state intact.
For example, BFT-Store~\cite{qi2020bft} performs erasure coding on the blocks to reduce the storage complexity per block to $O(1)$.
EIP-4844~\cite{eip4844} of Ethereum proposes to shard \emph{blob}, a special kind of block data only whose commitment is accessible by the transactions.
As previously discussed, these solutions are not desirable by blockchain databases.

The other works perform \emph{processing sharding} like regular distributed databases -- each node processes a subset of the transactions that only make use of the state shard(s) it stores.
\footnote{
    In some works, \emph{shard} (or node shard) refers to the group of nodes that work on certain state shard.
    Following distributed database's convention, in this work shard means \emph{data shard} and always refers to state shard.
}
The immediate effect of a reduced processing quorum is low fault resiliency, \eg, $\frac{1}{4}$~\cite{luu2016secure,kokoris2018omniledger,eyal2016bitcoin,dang2019towards} or $\frac{1}{3}$ within each processing quorum~\cite{el2019blockchaindb,amiri2021sharper}.

Besides the security concern, some works randomize the shards that the nodes work on and reshuffle the formation frequently on an epoch basis~\cite{luu2016secure,dang2019towards,yu2020ohie}.
This approach not only in advance degrades to probabilistic safety guarantee, but also the processing sharding that operates in this fashion cannot scale out the state because the nodes have to maintain the whole state to prepare for working on any shard in the following epochs.
Moreover, cross shard transactions bring additional coordination overhead to processing sharding approach, posing performance penalty and complicating the reasoning of safety~\cite{dang2019towards}.
Database transaction workload are also identified to bring inefficient processing to sharded blockchains~\cite{hong2024gridb}.

\paragraph{Decouple sharding from processing.}
To summarize, state sharding is desired for scaling out blockchains like databases, while global processing is desired for solid security.
However, this design space is rarely exploited.
Quote a survey of sharding replication systems from 2023~\cite{solat2023sharding}:
\emph{To the best of our knowledge, actually there is no protocol that uses storage sharding without processing sharding.}

Decoupling sharding from processing is challenging.
The storage layer must mask the missing shards prior to processing and synchronize them from storing nodes in time.
The synchronized shards must prove their \emph{integrity} \ie their contents are not tampered by the faulty storing nodes.
And most importantly, Byzantine faults must not cause any \emph{liveness} issues by withholding the storing shards.
