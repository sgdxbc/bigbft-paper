\section{Motivation}
\label{sec:bg}

\paragraph{Problem settings.}
In this work we target the BFT replications protocols that perform state machine replication (SMR) over states that potentially cannot fit into single node's storage.
We don't assume any specific structure of the state, only requires it to be compatible for \emph{sharding}~\cite{corbett2013spanner}.
\lijl{Is there a proper ``compatibility'' definition?}
The number of shards is also not significant, though sufficient shards (\ie much more than the number of nodes) can achieve a better load balance effect.
Examples of compatible states are key-value stores (atop what relational databases potentially build)~\cite{corbett2013spanner} and (Merkle) Patricia Trie~\cite{mpt} used by Ethereum.

We also do not assume any specific structure of the transactions, which may range from simple key-value updates to complex smart contracts.
We only expect that most transactions in the workload access only single or few shards (\ie online transaction processing (OLTP) workload instead of online analytical processing (OLAP)).
This expectation is valid for extensive scenarios such as token transfer between a pair of accounts or status update of a specific merchandise in a supply chain.
Besides, OLAP workload that scans over large number of shards can be performed off-chain with a verified state snapshot.

\paragraph{Blockchain databases.~\cite{ruan2021blockchains}.}
In blockchain databases, clients \emph{outsource} the database storage to the blockchain, which consists of the nodes with abundant storage capacity but are mutually untrusted to each other.
The common database operations \eg SQL queries are implemented on top of the BFT replication, realizing the user experience of database applications while tolerating Byzantine faults at the same time\cite{el2019blockchaindb,peng2020falcondb}.
Also, \cite{nathan2019blockchain} approaches the goal by plugging an ordering service into databases.

Scaling out blockchain state has been the recurring topic of blockchain databases.
As the blockchain databases keep operating, the size of content they store may ever grow.
However, blockchains, as state machine replication protocols, by default require each node to store a full copy of the state in order to replicate the execution individually.
Eventually, the ever-growing database will overwhelm the storage capacity of the nodes.
Some blockchain databases leverage the inherent structure of rational databases and decompose the databases into table-level sub-chains~\cite{el2019blockchaindb}.
The researches go further by utilizing authenticated data structures~\cite{martel2004general, tamassia2003authenticated} to safely process cross table queries (\eg join operations)~\cite{zhang2015integridb,hong2024gridb}.
However, more universal solutions that are compatible with single large table or even agnostic to state structure are demanded for more widely adoption.

\paragraph{Sharded blockchains}
One layer down, the blockchains can divide the stored data into shards\cite{corbett2013spanner} and each node stores only one or a subset of the shards.
However, without the whole state, the nodes can no longer process every transaction.
EIP-4844~\cite{eip4844} of Ethereum bypasses this limitation by sharding \emph{blob}, a special kind of block data only whose (succinct) commitment is fully replicated and accessible by the transactions.
This approach is not desirable by blockchain databases which requires the whole data to present in the state.

Currently, the sharded blockchain works perform \emph{processing sharding} like regular distributed databases -- each node processes a subset of the transactions that only make use of the state shard(s) it stores.
\footnote{
    In some works, \emph{shard} (or node shard) refers to the group of nodes that work on certain state shard.
    Following distributed database's convention, in this work shard means \emph{data shard} and always refers to state shard.
}
The immediate effect of a reduced processing quorum is low fault resiliency (unless when reaching out for synchronous BFT protocols~\cite{zamani2018rapidchain}), \eg, tolerating $\frac{1}{4}$ faulty nodes globally~\cite{luu2016secure,kokoris2018omniledger,eyal2016bitcoin,dang2019towards} or $\frac{1}{3}$ faulty nodes locally within each processing quorum~\cite{el2019blockchaindb,amiri2021sharper}.
\lijl{Since compromised security/correctness guarantee is a major concern, we should elaborate this part.}
Monoxide~\cite{wang2019monoxide} introduces Chu-ko-nu mining to recover a 50\% resiliency of faulty mining power, but its safety statement is built upon the assumption of dominance of the professional mining facilities that will perform batch-mining simultaneously on every shard, and the approach is limited to PoW setup.
\lijl{Not sure if we need to talk about this work.}

Besides the security concern, some works randomize the shards that the nodes work on and reshuffle the formation frequently on an epoch basis~\cite{luu2016secure,dang2019towards,yu2020ohie,zamani2018rapidchain}.
This approach not only in advance degrades to probabilistic safety guarantee, but also the processing sharding that operates in this fashion cannot scale out the state because the nodes have to maintain the whole state to prepare for working on any shard in the following epochs.

Last but not least, cross shard transactions bring additional coordination challenges.
They either pose performance penalty and complicate the reasoning of safety (potentially relying on the client~\cite{kokoris2018omniledger}), or the sharded blockchains give up atomicity and relax the linearizable guarantee~\cite{luu2016secure} or even completely overlook cross shard transactions~\cite{li2020polyshard}.
Database transaction workload are also identified to bring inefficient processing to sharded blockchains~\cite{hong2024gridb}.

\paragraph{Decouple sharding from processing.}
\lijl{We should have a dedicated ``Approach'' section that discusses our insights and design principles.}
To summarize, state sharding is desired for scaling out blockchains like databases, while global processing is desired for solid security.
However, this design space is rarely exploited.
Quote a survey of sharding replication systems from 2023~\cite{solat2023sharding}:
\emph{To the best of our knowledge, actually there is no protocol that uses storage sharding without processing sharding.}

Decoupling sharding from processing is challenging.
The storage layer must mask the missing shards prior to processing and synchronize them from storing nodes in time.
The synchronized shards must prove their \emph{integrity} \ie their contents are not tampered by the faulty storing nodes.
And most importantly, Byzantine faults must not cause any \emph{liveness} issues by withholding the storing shards.
