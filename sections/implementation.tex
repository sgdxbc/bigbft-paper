\section{Implementation}
\label{sec:impl}

\subsection{Authenticated storage.}

In this section, we discuss several candidate constructions for the authenticated dictionary abstraction required by \sys, detailed in \autoref{sec:design}.
Each construction offers different trade-offs in terms of storage and computation overheads and practicality.

\paragraph{Merkle trees.}
The classic approach to building an authenticated dictionary is to use a Merkle tree~\cite{merkle1987digital}.
The key-value pairs are organized in a tree structure, where each leaf node corresponds to a key-value pair, and each internal node contains the hash of its child nodes.
The commitment is the root hash of the tree.
To \open or \update a value, the server provides an \emph{authentication path} as the proof or update information, which consists of the hashes of the sibling nodes along the path from the leaf node to the root.
The client can \verify the proof by recomputing the hashes along the path and comparing the resulting root hash with the commitment, or it can \cupdate the commitment by updating the hashes along the path accordingly.

Merkle trees are simple and widely used.
Merkle Patricia Trie, a dense variant of Merkle tree, is used in Ethereum~\cite{wood2014ethereum} to organize the state data.
The sparse variant features Jellyfish Merkle tree~\cite{gao2021jellyfish}, a modern construction that is specifically designed for optimal write amplification in log-structured storage like RocksDB and is used in Libra/Diem and Aptos.

The main drawback of Merkle trees is that \open and \update operations have an $O(\log n)$ read overhead, where $n$ is the number of key-value pairs in the dictionary.
Recent study shows that this overhead can be significant in practice~\cite{li2024lvmt}.
Nonetheless, Merkle trees can be a good fit for the cases where the application also requires an authenticated storage for, e.g., \open to external clients and choose Merkle trees as the authenticated dictionary construction.
In such case \sys can directly leverage the existing Merkle tree without introducing additional overhead.
Also, the recent QMDB~\cite{zhang2025qmdb} construction decouples the Merkle tree into in-memory nodes and on-disk entries, achieving \open and \update with 1 disk read.
While the work didn't mention stateless updatability, it's straightforward to extend it to support \cupdate by providing the authentication path as the update information.
QMDB shows great potential to be an efficient authenticated dictionary construction for \sys.

\paragraph{Vector commitments~\cite{nitulescu2021sok}.}
Vector commitments (VCs) provide similar authentication functionalities as Merkle trees but with vectors (arrays) as the underlying data structures.
VC schemes support the following operations as defined in~\cite{catalano2013vector}:
\begin{itemize}
    \item \textsc{Setup}$(1^\lambda, n)$: generates public parameters $pp$ for a vector of size $n$.
    \item \textsc{Commit}$(\mathbf{v}, pp)$: generates a commitment $C$ for vector $\mathbf{v}$ using public parameters $pp$.
    \item \textsc{Open}$(\mathbf{v}, i, pp)$: generates a proof $\pi$ for the $i$-th element $v_i$ of vector $\mathbf{v}$.
    \item \textsc{Verify}$(C, v_i, i, \pi, pp)$: verifies that $\pi$ is a valid proof for $v_i$ in commitment $C$.
    \item \textsc{Update}$(C, v_i, v_i', i, pp)$: updates the commitment $C$ to reflect the change of the $i$-th element from $v_i$ to $v_i'$.
\end{itemize}
Mapping an authenticated dictionary to a vector is straightforward: we can treat the dictionary as a sparse vector, where each key corresponds to an index in the vector, and the value is stored at that index.
The \cupdate operation of the authenticated dictionary can be directly mapped to the \textsc{Update} operation of the VC scheme with the previous value $v_i'$ as the update information, and the \update operation could be a plain array update.

VC schemes feature $O(1)$ read overhead for \open and \update operations, significantly improving the performance compared to Merkle trees.
They usually support batch \open and \update efficiently as well.
One limitation of VC schemes is that they require a fixed vector size determined at setup time, making them less practical for dynamic workloads where the number of key-value pairs can grow over time.
Recent works~\cite{leung2022aardvark} address this limitation with multiple VCs.
The main drawback of VC schemes is their relatively high computation overhead, especially for the \update operation, which involves expensive cryptographic operations and are magnitudes of times slower than Merkle trees.
Nevertheless, VC schemes are actively studied, and their constant complexity makes them a promising direction for efficient authenticated dictionaries.

\paragraph{Trusted execution environment.}
Another approach to building an authenticated dictionary is to leverage trusted execution environments (TEEs) such as Intel SGX or AWS Nitro Enclaves.
TEEs provide a secure enclave where code and data can be executed and stored with strong confidentiality and integrity guarantees, even in the presence of a compromised server.
Furthermore, TEEs support remote attestation, allowing clients to verify that the code running in the enclave is genuine and has not been tampered with.
To build an authenticated dictionary using TEEs, the server runs the dictionary operations inside the enclave.
The nodes maintain an accumulated fingerprint of the \bump operations, e.g., by recursively hashing the previous fingerprint with the current operation, as the commitment.
The fingerprint maintained inside the enclave cannot be tampered with by the faulty replica nodes.

To \open a value, the enclave provides the value along with the current fingerprint and a remote attestation over both of the value and the fingerprint as the proof.
The client can \verify the proof by checking the remote attestation and comparing the fingerprint with the expected one.
The biggest advantage of using TEEs is to eliminate the update information for \cupdate operations.
The client can \cupdate the commitment with the \bump updates locally without requiring any update information from the server, significantly reducing the communication overhead.

In \autoref{sec:eval}, we evaluate our prototype with a TEE-style authenticated dictionary implementation.
The employed implementation has $O(1)$ read overhead for \open operations and no read overhead for \update operations, and we assume a trivial cost for \verify and \cupdate operations.
This setting not only closely approximates the performance of TEE-based authenticated dictionaries but also serves as a reasonable projection for future Merkle tree or VC-based implementations with optimizations.

\subsection{Optimizations}

\paragraph{Mask \fetch latencies by concurrent fetches and bounded staleness.}
The on-path retrieval of \fetch introduces latency penalties, ranging from microsecond to millisecond level when retrieving from geologically-distributed storage nodes.
Because the execution layer stalls until \fetch completes, the utilization is undermined, resulting in throughput degradation.
To recover the throughput, we introduce concurrent fetches.
The execution layer not only issue \fetch for the current transaction, but also pre-issues \fetch-es for the pending transactions in the execution queue.
By the time the transaction is ready to execute, its \fetch-ed values are likely already retrieved, allowing the transaction to proceed without stalling.

To perform concurrent fetches, the execution layer must predict the \fetch-es issued for the transactions before their proceeding transactions complete.
This is usually possible, and for certain common types of transactions (including UTXO ones), the \fetch-es can be completely determined by static analysis.
\gd{Remark that Ethereum smart contracts enforce explicit declaration of accessed keys.}
Nonetheless, for transactions whose \fetch-es cannot be (accurately) predicted, the execution layer can always issue on-path \fetch to execute the transactions.
\sys supports all kinds of transactions with an additional optimization for common types of transactions.

However, if the storage nodes can only respond to the retrieval requests for their current versions, they cannot respond to the concurrent \fetch-es before their trusted replica nodes \bump to the corresponding versions, and the sequential data dependency remains.
To address these, we introduce a bounded staleness semantic for \fetch.
The execution layer is configured with a staleness bound $s$, and it only issues \fetch-es for versions within $s$ of the current version.
At the same time, the storage nodes are configured with the same $s$, and they can respond to retrieval requests with values up to $s$ versions stale from the requested one.
Then, the execution layer further maintains a small in-memory cache of recent $s$ \bump operations.
When serving transaction reads, the cached updates supersede the \fetch-ed values if they overlap.
This cache not only guarantees to mask the staleness introduced by concurrent fetches but also potentially improves performance: if a hot key is frequently updated and fetched within a short period, the reads can be served directly from the cache and the performance is not affected by the \fetch at all.
