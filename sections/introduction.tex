\section{Introduction}
\label{sec:intro}

There is a trend to build databases out of blockchains.
\XXX.

There is a dilemma between scaling out the database state and blockchain's replicated execution.
The key of database's scalability is state sharding -- storage nodes can operate by storing only partial state \ie state shards.
As the result, databases can perfectly scale out to more storage nodes as the state size grows.
The storage capacity collaboratively contributed by arbitrary number of storage nodes can operate arbitrary large states without degrading performance.
Because the whole database is managed by a single central administration, the state updates \ie transactions only need to be performed by the nodes holding the relevant shards.
Single shard transaction can be performed locally, and for cross shard transactions, sophisticated methods are developed to minimize the overhead of ensuring ACID properties of them.

On the other hand, blockchains, essentially state machine replication protocols, demanding replicated execution on a quorum of nodes.
To tolerate Byzantine faults that deliver diverged execution results or withhold state, each correct node has to preserve a copy of the whole execution state and execute transactions individually.
The requirement of holding the whole database poses high entry barrier.
Indeed, the large execution states of popular blockchains have caused centralization tendency.

Previous works have studied sharded blockchain extensively, striving for better scaling out capability while preserving consistency.
\XXX
However, by sharding the processing of transactions, the trade-off between safety and scalability becomes fundamental.
More nodes participating a processing shard results in poorer scalability -- more copies of the shard state reside on these nodes, while less participant nodes can tolerate fewer faults.

What's worse, as the blockchain scaling out to more nodes, either scalability or security must be suffered, depending on whether the number of nodes participating a shard increases with the total number of nodes.

\xxx{Distinguish performance and storage scalability?}

Can blockchains scale out to more storage nodes like databases while deterministically tolerate $\frac{1}{3}$ Byzantine faults as BFT protocols?
In this work, we propose a new approach that \emph{independently scales out execution state to the execution}.
As in regular databases, the execution state is sharded and each node preserves only a subset of the shards.
At the same time, the global consensus (\ie Byzantine atomic broadcast) and execution are retained, and the safety guarantee is \emph{decoupled} with the sharding design.
With this approach, blockchains can persist the standard safety statement while enjoy perfect scale out feature like databases.

Independent scaling-out of execution state brings its unique challenges.
The relevant state shards must be efficiently dispersed by the storing nodes to all upon execution, the other nodes must be able to verify the state shards independently, and most importantly, the state shards must be available even if Byzantine nodes participate in storing them.
To solve these challenges, we deploy erasure code to disseminate the state shards to more than $\frac{2}{3}$ of all the nodes while keep a constant overall storage overhead of storing a state shard (\ie about 3x shard size).
Because of the high overhead of deploying erasure code online, we propose an alternative online process path that preserves constant number of verbatim copies of state shards on uniformly random nodes, achieving tunable probabilistic availability.
Both of the methods incurs constant overall storage overhead per state shard, same as databases.

To this end, we propose \sys, a practical BFT protocol designed for scaling out the replicated state.
\sys combines the two aforementioned methods, utilizing the verbatim copies as the \emph{active layer} and the erasure code as the \emph{archive layer}.
The active layer possesses the latest version of the state shards and serves the online execution with high probability.
At the same time, \sys periodically archives the state with erasure code as a fallback.
