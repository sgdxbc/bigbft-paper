\section{System Design}
\label{sec:overview}

\subsection{Preliminaries}

\paragraph{Authenticated dictionaries.}
The key-value state is stored in the form of \emph{authenticated dictionaries}, which allow untrusted servers to serve key-value queries with proofs that can be efficiently verified by clients holding only a short commitment, and the clients are able to update their commitments according to the updates and continuously verify the server responses against the mutable state.

Specifically, an authenticated dictionary scheme supports the following operations, following the definitions introduced by \cite{peng2020falcondb}.
\begin{itemize}
    \item \commit($D$): given a dictionary $D$, output a commitment $c$;
    \item \open($D, k$): given a dictionary $D$ and a key $k$, output the value $v$ associated with $k$ in $D$ and a proof $\pi$;
    \item \verify($c, k, v, \pi$): given a commitment $c$, a key $k$, a value $v$ and a proof $\pi$, output true if $\pi$ is a valid proof that $v$ is the value associated with $k$ in the dictionary committed by $c$, and false otherwise;
    \item \update($D, k, v$): given a dictionary $D$, a key $k$ and a new value $v$, output a dictionary $D'$ that updates the value associated with $k$ in $D$ to $v$, and an auxiliry update information $\delta$;
    \item \cupdate($c, k, v, \delta$): given a commitment $c$, a key $k$, a new value $v$ and update information $\delta$.
    If $\delta$ is valid, that is, it is the output of \update($D, k, v$) for some dictionary $D$ committed by $c$ (i.e., \commit($D$) outputs $c$), output true and the updated commitment $c'$ that commits to the updated dictionary $D'$; otherwise, output false and $\bot$.
\end{itemize}

The \cupdate operation enables clients to update their commitments in a \emph{stateless} manner, i.e., without needing to re-execute \commit on the entire updated dictionary from scratch.
In practice, clients only need to run \commit once at the beginning to obtain the initial commitment of an empty dictionary, and then can keep updating their commitments using \cupdate as the dictionary evolves.

There are multiple constructions of authenticated dictionaries based on different cryptographic primitives, varying in their computation and space efficiency.
\gd{cite}
We will discuss and compare these constructions in \autoref{sec:impl}.

\paragraph{Erasure coding.}

\subsection{Active Tier}

We divide the key space into multiple shards and store them across all storage nodes in the system.
For fault tolerance, each shard is replicated on $r$ storage nodes, referred as the \emph{responsible nodes} of the shard.
These $r$ nodes are selected randomly and independently for each shard using consistent hashing.
To \fetch the values of a shard, a replica node retrieves the values from the responsible nodes and returns the first correct response it receives.

To ensure storage scalability, $r$ is a constant independent of the total number of storage nodes and may be less than $f$.
However, since the placement of shards is randomized, the probability that all $r$ nodes storing a shard are faulty decreases exponentially with $r$, regardless of the total number of storage nodes.
As long as there is at least one correct node among the $r$ responsible nodes of a shard, the shard is available.
This random sampling technique has been widely adopted in previous sharded blockchain systems for their \emph{committee formation}.
\gd{cite.}
However, they require a much larger committee size (i.e., large $r$) to ensure at least $\frac{2}{3}$ of the committee members are correct with high probability, because their systems also rely on the committees for the correctness of execution.

Even if the availability of each shard is secured with high probability, a faulty storage node can still return incorrect or stale values for \fetch requests, jeopardizing the correctness of execution.
To combat this issue, we further employ the authenticated dictionary scheme where each shard is a separated authenticated dictionary, the storage nodes are servers and the replica nodes are clients.
The replica nodes maintain the lightweight commitments of all shards.
When retrieving values from the responsible nodes, the storage nodes \open the retrieved keys and response both the values and the proofs.
The replica nodes \verify the retrieved values using the proofs and their locally stored commitments and discard any malformed or stale values.
For \bump operations, the storage nodes receive the pushed updates from their trusted replica nodes.
The responsible nodes \update their local shards and get the update information, while the other storage nodes ignore the updates.
Then, every replica nodes retrieve the update information from the responsible nodes and \cupdate their local commitments.

The storage nodes need to respond to retrieval requests from multiple replica nodes, potentially on different versions of the state.
As the result, the retrieval requests should be tagged with the version of the state they are issued for, and the storage nodes must maintain past values and proofs of the retrieved keys to serve these requests.
Notice that the storage nodes do not need to maintain the entire past state shards, but only the values of keys that have been accessed by the trusted replica node in previous versions.
As discussed in \autoref{sec:approach}, SMS expects a consistent sequence of \fetch invoked from the replica nodes, so the storage nodes can simply treat any retrieval on the unexpected keys as malformed requests and ignore them.
Nonetheless, the storage nodes must perform garbage collection on the past values to bound their memory overhead, which we detail after introducing the archive tier.

\subsection{Archive Tier}

The active tier can achieve correctness and probabilistic availability with decent performance.
However, probabilistic availability may not be sufficient in some scenarios.
It is also vulnerable to a slowly adaptive adversary that can compromise nodes over time. \gd{cite}
To achieve deterministic availability, we introduce the archive tier.
\lijl{Does this deterministic availability depend on properties of the active tier?} \gd{No and explain here.}
In a nutshell, the archive tier periodically \emph{checkpoints} the entire state stored in the active tier using erasure coding.
The checkpoint will be \emph{deterministically} available as long as no more than $f$ nodes are compromised.
So that, even if the active tier loses some shards due to probabilistic failure or slow adaptive attacks, the system can always restart from the last checkpoint and \emph{reconfigure} the active tier to bring it back to an operational state.

To checkpoint the state, the storage nodes first agree on a specific version of the state to checkpoint by voting via atomic broadcast.
\lijl{This statement is a bit ambiguous. This is a past version or a future version? Any specific requirement on the version?} \gd{Clarified.}
The version where $2f+1$ storage nodes have voted is selected as the checkpoint version.
Each storage node snapshot the checkpoint version of their responsible shards and gather all the shards with a retrieval protocol similar to \fetch.
Each node then individually encodes the gathered shards using an RS($3f+1$, $f+1$) erasure code, dividing the original state into $f+1$ chunks and producing $2f$ parity chunks.
Finally, the node stores the hashes of all $3f+1$ chunks and retains only one chunk according to its node index.
The nodes signal the completion of checkpointing via voting the next checkpoint version.
By starting a new round of checkpoint, the nodes learn that the previous checkpoint has been completed and can safely discard the transaction history and past values and proofs up to the checkpointed version and the stored hashes and chunk of the checkpoint(s) prior to the previous one.

After a checkpoint is completed, it is deterministically available (until the next checkpoint is completed).
This is because a checkpoint completes with at least $2f+1$ votes, among which at least $f+1$ are from correct nodes, who have encoded the state and stored a chunk.
The RS($3f+1$, $f+1$) erasure code guarantees that any $f+1$ chunks are sufficient to reconstruct the original state.
Thus, those $f+1$ voted correct nodes always host enough chunks to reconstruct the original state.
\lijl{It is not immediately clear how does the original $f+1$ shards are available during this encoding process based on this line of reasoning.} \gd{Clarified.}
When the retrieval for the \fetch or the following checkpoint stalls, the replica nodes vote to trigger a recovery and reconfigure process via atomic broadcast.
The votes provide a random seed, according to which the $r$ responsible nodes of each shard are re-selected.
The storage nodes then retrieve the last checkpointed chunks from all nodes, verify their integrity using the stored hashes, and reconstruct the original state.
Finally, they re-shard the state and store them according to the new shard placement.

The description above requires the storage nodes to hold the entire state during the encoding process.
To avoid this infeasible requirement, we further divide the entire state into multiple \emph{stripes}, each containing multiple shards.
The active tier operates each stripe independently, and the archive tier checkpoints and reconstructs each stripe sequentially.

The active and archive tiers defend slowly adaptive adversaries together.
The archive tire can checkpoint the state as long as the adversary has not compromised $f+1$ nodes, and it can reset the active tier from the compromised state.
As long as the adversary cannot compromise $f+1$ nodes between two consecutive checkpoints, the system can keep available.
As we will see in \autoref{sec:eval}, the checkpoint can be finished within reasonable time intervals.

\subsection{Reasoning about Properties}

In the previous sections, we focused primarily on the intuition behind the correctness and availability properties.
\gd{If necessary, add a formal proof sketch in the appendix?}
We now analyze the storage overhead.
For simplicity, we analyze the storage overhead from the perspective of a single stripe, as the stripes are independent and identical in design.
We also only consider the storage overhead of shards and checkpoints, as the other metadata (e.g., past values and proofs, update information, hashes) are negligible and reside in memory.

The active tier stores $r$ replicas of each shard, and its total storage is $r$ times the state size.
The archive tier stores the checkpoint which is $\frac{3f+1}{f+1} < 3$ times the state size.
During checkpointing, the storage overhead is temporarily doubled as each shard is snapshotted and two checkpoints coexist.
Thus, the total storage overhead of the system is at most $2(r+3)$ times the state size.
Since $r$ is a constant independent of the total number of nodes, we achieve storage scalability.
