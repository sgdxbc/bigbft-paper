\section{System Design: An Iterative Refinement}
\label{sec:overview}

In this section we describe our design of the storage layer of \sys, and resort to off-the-shelf Byzantine atomic broadcast protocols for the consensus layer.
The storage layer is fed with a (potentially infinite) list of transactions ordered by the consensus layer.
It should bring the accessed state shards of the transactions available on every node, then the transaction is processed, and the shards are updated.
In the following we consider the state as a piece of multi-versioned shared data, and by processing a transaction the nodes bring the state into a new version.

The consensus layer guarantees to produce a consistent list of transactions on every (correct) node.
The main goal of designing the storage layer is to ensure two properties: storage scalability (\autoref{sec:bg}) and availability (\autoref{sec:approach}).
The former property requires the storage layer to store bounded number of shards of all versions at any time on every node.
And the latter one means every node can either access every shard of the current version (so it can process arbitrary transaction against it), or it can access every shard of a newer version (because a supermajority of nodes has advanced to it), and it can verify the correctness of these shards and accept to skip to this version.

For easy understanding, we iteratively describe the design and reason about the desired properties for each iteration.
We start with a simple design I1, refine its redundancy level with I2, combine I1 and I2 together into a generational design to amortize the coding overhead in I3, and finally combine a modified version of I1 with I2 as I4 for a better usability.

\paragraph{I1: Sharding + plain replication.}
In the simplest design, each shard is placed on $f+1$ nodes and the placement (\ie which shard is stored by which nodes) is assigned by consistent hashing~\cite{karger1997consistent}.
All the shards are organized into a Merkle tree~\cite{merkle1987digital}, and nodes maintain inclusion proofs for its storing shards.
For each transaction, nodes first synchronize necessary shards of its current view, then process the transaction, update inclusion proofs of its stored shards and bump state version.
To synchronize a shard, nodes may query $f+1$ nodes and wait for one reply with valid inclusion proof.
The old version of the state, \ie the shards and their inclusion proofs, are not discarded immediately to serve future queries from other (slower) nodes.

The availability can be easily argued: every version of every shard is served by $f+1$ nodes and at least $1$ of them will serve it correctly.
Also, all correct nodes must have consistent views of each version of the state because they reach the version by processing identical sequence of transactions.
So the inclusion proof produced by one node can be verified on another one \ie the shard that is valid to its storing node is valid to every node.

\paragraph{Garbage collection.}
\lijl{What is the guarantee of GC? No correct node needs the older version? The new version is available?}
\gd{Defined in C1.}
First, each shard is placed on $2f+1$ nodes instead of $f+1$.
Safety is not affected by additional redundancies, obviously.

Nodes broadcast when they bump state version (which can be trivially implied by querying for next version).
A $2f+1$ bump quorum (of certain version) is a certificate to garbage collect all (meta)data below that version.

Safety: if $2f+1$ nodes have bumped up to a version, at least $f+1$ of them are correct.
For each shard (of that version), the $2f+1$ nodes that ought to serve it must intersect at least one correct node with this $f+1$ correct nodes, who will serve the shard.

Liveness: as long as the upper layer consensus protocol guarantees the liveness of $2f+1$ correct nodes, quorums of increasing versions that consist only correct nodes will always form soon or later.

\paragraph{I2: Erasure coding.}
The I1 design incurs $2f+1$ redundancy, which grows linearly to the number of nodes \ie the total storage capacity.
The storage efficiency gets worse with more storage resource, and this is just a constant factor (\ie $\frac{2}{3}$) storage compression to the baseline.

The refined design is to deploy a RS$(k+2f,k)$ erasure code, that is, for each stripe that contains $k$ shards, we generate $2f$ parities, and store them on $k+2f$ distinct nodes (which implies $k\leq{}f+1$), which forms the placement group of the stripe.
The load and store operations are amplified to stripe level.
To load a stripe, a node can query any $k$ nodes in the placement group and decode it.

Both shards and parities are organized into the Merkle tree, so nodes can also check the validity of the received parities before decoding.

Execution: for each \emph{shard stripe} involved in read set and write set, query $k+2f$ nodes and wait for $k$ replies to either directly retrieve or reconstruct the stripe shards.
Execute transaction and apply updates to the shards of write set.
Regenerate the parities of the updated stripes, store updated shards and parities according to the placement, recalculate the inclusion proofs of all storing shards and parities, and bump state version.

Safety: for each stripe, at least $k+f$ of its shards/stripes will be served correctly, so the stripe will always be reconstructible.

For garbage collection, the bump quorum still requires only $2f+1$ nodes, which includes at least $f+1$ correct nodes.
For each stripe, the $2f+k$ nodes that ought to serve it must intersect at least $k$ correct node with this $f+1$ correct nodes, who serve sufficient shards/parities to reconstruct the stripe.

\paragraph{Analyze redundancy.}
The redundancy of deployed RS$(k+2f,k)$ erasure code is $\frac{k+2f}{k}$.
With $k=1$ the redundancy is $2f+1$ and this essentially is the plain replication design.
With $k=pf$ where $p\in(0,\frac{f+1}{f}]$, the redundancy is $\frac{p+2}{p}$ and remain constant with varying state size and total storage capacity, achieving the scalability goal.

However, this also means that when $f$ increases (\ie more nodes joining), $k$ increases as well, and we have to dynamically adjust the number of shards of a stripe.
Thanks to convertible code, we are able to merge multiple stripes into single one (with multiplied $k$) with lightweight computation by merging the parities of the original stripes, mitigate the overhead of massive transcoding.
\lijl{This should be part of the reconfiguration protocol?}

Note that even if $k$ is not adjusted according to increasing $f$, the safety is not violated, and we are just paying for additional redundancy overhead.
On the other hand, when $f$ is decreasing, $k$ must be decreased and the stripes must be reconstructed immediately.
Nevertheless, when $n$ is increasing, $f$ must be increased immediately but $k$ is not required to do so; while when $n$ is decreasing, $f$ is not required to be decreased immediately (except concerning liveness), and administrator can only decrease $f$ when it's a proper timing to decrease $k$.
\lijl{We would carefully design a reconfiguration protocol.}

\paragraph{I3: Amortize erasure code overhead with generational design.}
The I2 design incurs frequent encoding and decoding operations.
First, although each parity is stored on only single node, every (correct) node has to encode it to construct inclusion proofs for other shards/parities (it stores).
Second, although RS code is systematic and nodes can skip decoding if all the stripe shards are replied, that only happen when all $k$ stripe shards are stored by correct nodes.
Even if in the case where the $\frac{1}{3}$ faulty nodes do not use any sophisticated strategy and just withhold the shards they store, the probability of at least one parity is withheld by faulty nodes is $1-(\frac{2}{3})^k$, which is undesirably significant.

To overcome this drawback, we adapt an \emph{epoch}-based \emph{generational} approach.
The new state versions are created in the \emph{young} generation, whose shards are replicated on $f+1$ nodes as in the I1 design.
Periodically, the nodes enter new \emph{epochs} and reach consensus on the \emph{epoch versions}.
After the bump quorum is collected for an epoch version, the state of the epoch version is moved into \emph{old} generation and erasure coded.
The (extra) copies of the shards from the young generation can be released.

At first glance the young generation adds an $f+1$ extra redundancy (as in I1) and defeats the scalability goal.
However, the $f+1$ shard copies are only for the shards updated in the current epoch; under many (skewed) workloads and with proper epoch interval, the portion of updated shards is tiny.
\lijl{We should show that in real-world workloads, the working set size is typically constant, independent of the overall storage size.}
Nevertheless, it does not fit all kinds of workloads, and faulty nodes can still perform withhold attacks at the beginning of each epoch.
This is solved in the next design.

\paragraph{I4: Achieve constant redundancy with probabilistic (fast path) availability.}
In this design we exploit the fact that the old generation can solely provide hard availability guarantee and relax the availability guarantee of the young generation.
Inspired by \cite{qi2020bft} (though in their work, the availability of blocks instead of state is concerned), we repropose the young generation as a shortcut and adapt probabilistic availability.
Instead of storing $f+1$ copies, the young generation preserves a fixed number of $c$ copies for each shard on uniformly random nodes regardless of $f$.
Furthermore, the young generation preserves copies for \emph{all} active shards \ie the most advanced version of every shard, even if it has been copied into the old generation.
Thus, from this point we call the young and old generations the \emph{active} and \emph{archive} layers.

Safety: for all version, every stripe is safe by replaying the transactions from the last archived version, and the safety of the archived state is as discussed in the I2 design.
Additionally, the probability for each shard to be served by the active layer is $1-\frac{1}{3^c}$, which is more than 99.9\% with $c=7$ and more than six-nines with $c=13$.
The robustness of active layer increases exponentially to $c$ and is configurable by administrator.
Note that this does not turn the upper layer BFT into speculative consensus and does not require the service state machine to support rollback: in the rescuing case where the shards are not available on the active layer, the ledger history is not lost, and the nodes just re-execute the same transaction sequence.
Whatever replies have been committed on clients will not be invalidated.
