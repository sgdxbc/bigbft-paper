\section{System Design: An Iterative Refinement}
\label{sec:overview}

In this section, we detail the design of the state management system (SMS) within \sys.
SMS considers the managed state as multi-versioned data, with each transaction execution generating a new state version.
On shard level, in each new version a fraction of shards is updated by the interleaving transaction, and the other unmodified shards ``fall through''.
It exposes three interfaces to the execution layer:
\begin{itemize}
    \item \texttt{get}(shard indexes) returns state shards of current version.
    \item \texttt{update}(shard indexes, shards) update the shards and bump (\ie, increment) the state version.
    \item \texttt{skip}() fast-forward the state version and returns the number of skipped versions.
    We will elaborate on this later.
\end{itemize}

SMS guarantees availability (\autoref{sec:approach}).
Regarding the interfaces, it means all \texttt{get} will return the desired shards successfully (with the exception described later).
On the other hand, execution layer should guarantee safety to SMS, which means the correct nodes will call \texttt{update} with identical sequence of shard indexes and shards.
If so, then SMS guarantees that \texttt{get} returns identical shards on all correct nodes.
Conceptually, SMS behaves as the full state is maintained on every node.

However, to accomplish scalable storage consumption, SMS cannot store all shards on all nodes and the nodes have to load some shards remotely upon \texttt{get}.
If a node lags behind a $2f+1$ supermajority, it is possible that the loaded shard is \emph{garbage collected} through the procedure detailed later, and \texttt{get} returns null.
In such case, the node can call \texttt{skip} to catch the pace, fast-forward its version and skip execution for the intermediate transactions.
In another word, SMS guarantees the availability of a \emph{sliding window} of state versions, and the nodes fall behind this window can always catch up by calling \texttt{skip}.
This fact allows us to reason about the liveness of \sys: nodes can always make progress on the state version (given that there are new versions ahead) either by calling \texttt{update} followed by \texttt{get} that is guaranteed to succeed or by calling \texttt{skip}.

\paragraph{Garbage Collection.}
I1 becomes practical only if historical versions of the shards can be pruned.
To enable this, we first modify I1 such that each shard is placed on $2f+1$ nodes instead of $f+1$, and they are all queried for loading the shard.
This certainly won't fail any \texttt{get} calls.

Next, after bumping their state version at the end of \texttt{update}, nodes broadcast signed messages.
These messages include the node's Merkle root representing its view of that state version it just entered.
A $2f+1$ bump quorum with matching version and Merkle root serves as a certificate to garbage collect all shards and metadata from the versions prior to the certified one. \lijl{meaning both metadata and shard data?}\gd{Yes and udpated.}
Once a node gathers such a bump quorum certificate, it can prune its historical shards accordingly.

If $2f+1$ nodes have bumped up to a certain version, at least $f+1$ of them are correct.
For any given shard of that version, the $2f+1$ nodes responsible for storing it must overlap with these $f+1$ correct nodes by at least one correct node, which will serve the shard and correctly respond to \texttt{get}.
As the result, \texttt{get} every shard of the \emph{highest} version certified by a bump quorum will succeed.
Simultaneously, the bump quorum certificate also indicates the correct Merkle root (view of the state) for that version.
So, if the incoming query is for a shard versioned older than the last bump quorum certificate, the nodes can respond with the certificate instead of the shard.
This causes the corresponding \texttt{get} to return null, but in a following \texttt{skip} call, the querying node can fast-forward to the certified version and set its view of the state to the certified Merkle root.
Therefore, it is safe for the nodes to discard all the shards older than the last certified version.

\ifspace
Also, the liveness of garbage collection is straightforward, as the formation of a bump quorum can be done by the $2f+1$ correct nodes.
During periods of synchrony, bump quorum certificates for increasingly newer versions will become available, and the garbage collection process will prune historical shards, allowing nodes to operate while storing a bounded number of shards.
\fi

\paragraph{Redundancy Analysis.}
The redundancy introduced by the EC$(k+2f,k)$ erasure code is $\frac{k+2f}{k}$.
When $k=1$, the redundancy becomes $2f+1$, which is equivalent to the plain replication design I1.
By setting $k=pf$, where $p$ is a constant in the range $(0,\frac{f+1}{f}]$, the redundancy becomes $\frac{pf+2f}{pf} = \frac{p+2}{p}$. This redundancy factor remains constant regardless of the state size and total storage capacity, thus achieving the desired storage scalability property.

However, this also implies that as $f$ increases (\ie, more nodes join the system), $k$ should ideally increase as well to maintain a target redundancy ratio.
This necessitates dynamically adjusting the number of shards within a stripe.

This approach mitigates the significant overhead of massive transcoding operations\footnote{
It's important to note that even if $k$ is not adjusted immediately with an increasing $f$, the safety of the system is not compromised; we would simply incur a higher redundancy overhead than necessary.
Conversely, when $f$ decreases, $k$ must be reduced, and the stripes need to be reconstructed promptly.

Nevertheless, when the total number of nodes $n$ increases, the potential number of faults $f$ also increases, but an immediate increase in $k$ is not strictly required.
Conversely, when $n$ decreases, $f$ does not necessarily need to be decreased immediately (except for potential liveness considerations), and the administrator can choose an opportune time to decrease $f$ and consequently $k$.

\paragraph{I3: Amortizing Erasure Code Overhead with a Generational Design.}
\ifspace
The I2 design involves frequent encoding and decoding operations, leading to two primary overheads.
First, although each parity shard is stored on only one node, every node must encode the original state shards to generate inclusion proofs for the state shards and parity shards it stores.
Second, while nodes can avoid decoding if all the shards within a queried stripe are successfully retrieved, this scenario only occurs when all $k$ original state shards of the stripe are stored by correct nodes.
Even if the $\frac{1}{3}$ faulty nodes employ no sophisticated strategy and simply withhold the shards they store, the probability that at least one required original state shard is stored and withheld by a faulty node is lower-bounded by $1-(\frac{2}{3})^k$.
This probability is undesirably significant and increases with $k$.

\else
The previous iteration is effective but incur on-path encoding operations, and faulty nodes can easily trigger massive decoding operations simply by withholding stored shards.
\fi
\gd{Updated.}
To effectively resolve this drawback, we adopt an epoch-based \emph{generational} approach.
New state versions are created in the \emph{young} generation, where shards are replicated on $f+1$ nodes, similar to the I1 design.
\lijl{it is not immediately clear that only shards that are modified by transactions are replicated}\gd{Done in I1.}
Periodically, the nodes transition into new \emph{epochs} and reach consensus on specific \emph{epoch versions} (through the consensus layer).
Once a bump quorum is achieved for an epoch version, the state corresponding to that epoch version is moved into the \emph{old} generation and encoded using the erasure code.
The redundant copies of the shards from the young generation can then be discarded.
Since all shard loading requests are served from the young generation, the encoding of the old generation can be performed in the background.
This ensures that the process of loading shards is free from any encoding or decoding overhead.

\gd{Updated.}
The availability of I3 is guaranteed by the availability properties of both I1 and I2.
Initially, the young generation seems to introduce an $f+1$ redundancy (as in I1), potentially undermining the storage scalability objective.
However, thanks to the copy-on-write optimization, these $f+1$ shard copies are only maintained for the shards that are updated within the current epoch.
In many real-world applications, workloads exhibit high skewness, and the size of the frequently accessed ``working set'' of data tends to be bounded and independent of the total state size.
Nevertheless, this approach might not be optimal for all workload patterns, and malicious nodes could still execute withholding attacks at the beginning of each epoch, affecting performance.
This limitation is addressed in the subsequent design.

\paragraph{I4: Achieving Constant Redundancy with Probabilistic (Fast Path) Availability.}
In this design, we capitalize on the fact that the archive layer \emph{alone} can ensure robust availability and optimize the storage overhead by \emph{relaxing} availability guarantee of the young generation, drawing inspiration from \cite{qi2020bft}\footnote{Their work focuses on the availability of blocks rather than state.}.
%  we repurpose the young generation as a fast path with probabilistic availability.
Instead of maintaining $f+1$ replicas, the young generation stores a fixed number $c$ of copies for each shard, distributed across uniformly random nodes, irrespective of $f$.
Moreover, the young generation retains copies of \emph{all} active shards, representing the latest version of every shard, even if that version has also been moved to the old generation.
Thus, we henceforth refer to the young and old generations as the \emph{active} and \emph{archive} layers, respectively.

Furthermore, the probability of loading a shard successfully with the active layer is $1-(\frac{2}{3})^c$, which exceeds 99.9\% with $c=7$ and surpasses six-nines with $c=13$.

The resilience of the active layer grows exponentially with $c$ and is configurable by the administrator.
Crucially, a potential failure of the active layer does not transform \sys into a speculative BFT protocol and does not necessitate rollback capabilities in the replicated state machine.
In the recovery scenario where shards are unavailable in the active layer, the transaction history remains intact, and nodes simply re-execute the same sequence of transactions assisted by the archive layer.
Any replies already committed to clients will not be invalidated.
\ifspace
Finally, storage overhead of the active layer is a fixed $c$ times the state size, so the per-node average overhead is inversely proportional to the number of nodes, \ie, is storage-scalable.
As already shown, the archive layer achieves storage scalability, as discussed in I2.
Therefore, I4 is a design that effectively achieves both availability and storage scalability.
