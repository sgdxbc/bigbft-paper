\subsection{Preliminaries}

\paragraph{Authenticated dictionaries.}
The key-value state is stored in the form of \emph{authenticated dictionaries}, which allow untrusted servers to serve key-value queries with proofs that can be efficiently verified by clients holding only a short commitment, and the clients are able to update their commitments according to the updates and continuously verify the server responses against the mutable state.

Specifically, an authenticated dictionary scheme supports the following operations, following the definitions introduced by \cite{peng2020falcondb}.
\begin{itemize}
    \item \commit($D$): given a dictionary $D$, output a commitment $c$;
    \item \open($D, k$): given a dictionary $D$ and a key $k$, output the value $v$ associated with $k$ in $D$ and a proof $\pi$;
    \item \verify($c, k, v, \pi$): given a commitment $c$, a key $k$, a value $v$ and a proof $\pi$, output true if $\pi$ is a valid proof that $v$ is the value associated with $k$ in the dictionary committed by $c$, and false otherwise;
    \item \update($D, k, v$): given a dictionary $D$, a key $k$ and a new value $v$, output a dictionary $D'$ that updates the value associated with $k$ in $D$ to $v$, and an auxiliry update information $\delta$;
    \item \cupdate($c, k, v, \delta$): given a commitment $c$, a key $k$, a new value $v$ and update information $\delta$.
    If $\delta$ is valid, that is, it is the output of \update($D, k, v$) for some dictionary $D$ committed by $c$ (i.e., \commit($D$) outputs $c$), output true and the updated commitment $c'$ that commits to the updated dictionary $D'$; otherwise, output false and $\bot$.
\end{itemize}

The \cupdate operation enables clients to update their commitments in a \emph{stateless} manner, i.e., without needing to re-execute \commit on the entire updated dictionary from scratch.
In practice, clients only need to run \commit once at the beginning to obtain the initial commitment of an empty dictionary, and then can keep updating their commitments using \cupdate as the dictionary evolves.

There are multiple constructions of authenticated dictionaries based on different cryptographic primitives, varying in their computation and space efficiency.

In an authenticated dictionary, or more generally, an authenticated data structure (ADS) scheme, an untrusted server answers queries over a data structure and returns a proof; a client maintains only a short commitment and verifies each reply.
Updates on the server are accompanied by update information that allows the client to efficiently update its commitment.
For authenticated dictionaries, the data structure is a key-value map, and the ADS scheme supports the following operations:
\begin{itemize}
    \item \commit($D$): given a dictionary $D$, output a commitment $c$;
    \item \open($D, k$): given a dictionary $D$ and a key $k$, output the value $v$ associated with $k$ in $D$ and a proof $\pi$;
    \item \verify($c, k, v, \pi$): given a commitment $c$, a key $k$, a value $v$ and a proof $\pi$, output true if $\pi$ is a valid proof that $v$ is the value associated with $k$ in the dictionary committed by $c$, and false otherwise;
    \item \update($D, k, v$): given a dictionary $D$, a key $k$ and a new value $v$, update the value associated with $k$ in $D$ to $v$, and output the update information $\delta$;
    \item \cupdate($c, k, v, \delta$): given a commitment $c$, a key $k$, a new value $v$ and update information $\delta$, output the updated commitment $c'$.

\end{itemize}

In our design, each shard is implemented as an authenticated dictionary.
The hosting node serves as the untrusted server, while the non-hosting nodes act as clients.
Non-hosting nodes maintain the commitment of the shard, initialized by committing to an empty dictionary.
When nodes retrieve keys from the hosting node, the hosting node opens the requested keys and sends the corresponding values and proofs to the non-hosting nodes.
The non-hosting nodes verify the values using the proofs and their locally stored commitment.
For \bump operations, non-hosting nodes obtain the update information from the hosting node and update their local commitment accordingly.
The authenticated dictionary scheme guarantees that the commitment remains consistent with the shard's content.
By verifying retrieved values through the authenticated dictionary, non-hosting nodes can detect and discard any malformed or stale values from the hosting node, thereby ensuring correctness.

To ensure the availability of each shard, we replicate every shard on $r$ randomly selected hosting nodes, determined by consistent hashing.
For storage scalability, $r$ is a constant independent of the total number of nodes and may be less than $f$.
Although there is a possibility that all $r$ nodes storing a shard are faulty, the randomized placement of shards mitigates this risk.
Thus, a key (and its corresponding shard) is stored by $r$ nodes, each of which is faulty with probability $\frac{f}{3f+1}$ independently.
Consequently, the probability that all $r$ nodes storing a shard are faulty is $(\frac{f}{3f+1})^r$, which decreases exponentially with $r$, regardless of the total number of nodes.
Therefore, the probabilistic availability of each shard can be ensured by choosing a sufficiently large $r$.
This level of guarantee is sufficient for some practical scenarios, and we will later discuss how to further achieve deterministic availability.

\paragraph{Garbage collection of past values.}
As previously mentioned, the hosting node stores not only the current shard but also the values of accessed keys from previous versions.
The number of past versions retained by the node must be bounded, requiring timely garbage collection of past values.
If garbage collection is delayed, the node must suspend further \bump operations to avoid excessive storage of past values.

As we will detail later, the archive tier periodically picks a version and archives it into erasure-coded shards.
This archived version is guaranteed to be recoverable by any node (before the next archive version is archived) and serves as an anchor point for garbage collection.
After participating the archiving of version $v$, a node can safely discard all past values prior to version $v$.
On the other hand, if a node is lagging behind the last archived version, it may not be able to retrieve the \fetch-ed values for its current version, as the hosting nodes may have already discarded those values.
The node can recover the last archived version from the archive tier and ask execution layer to \forward to that version.
\lijl{After \forward, all subsequent fetches can be served by the responsible node.}

The liveness of garbage collection is guaranteed by the liveness of archive tier.
As we will show, the archiving process requires only $2f+1$ nodes to participate and is guaranteed to be live.
Nonetheless, a faster garbage collection scheme is introduced in \gd{ref} to further reduce memory pressure of the nodes when all nodes are correct.

This garbage collection routine satisfies the availability property.
The \fetch and \bump operations can always proceed without returning \forward unless the node is lagging behind at least $2f+1$ other nodes.
If this is not the case, there will not be an archived version that is ahead of the node's version.
This ensures that \forward is only return on at most $f$ nodes.
On the other hand, if a node is lagging behind at least $2f+1$ nodes, it will eventually learn about the last archived version and return \forward, ensuring that \fetch and \bump operations eventually complete on every node.

\paragraph{Mask \fetch latencies by concurrent fetches and bounded staleness.}
The on-path retrieval of \fetch introduces latency pernalties, ranging from microsecond to millisecond level when retrieving from geologically-distributed nodes.
Because the execution layer stalls until \fetch completes, the utilization is undermined, resulting in throughput degradation.
To recover the throughput, we introduce concurrent fetches.
The execution layer not only issue \fetch for the current transaction, but also pre-issues \fetch-es for the pending transactions in the execution queue.
When a transaction completes, its \fetch-ed values are likely already retrieved, allowing the transaction to proceed without stalling.

To perform concurrent fetches, the execution layer must predict the \fetch-es issued for the transactions before their proceeding transactions complete.
This is usually possible, and for certain common types of transactions (including UTXO ones), the \fetch-es can be completely determined by static analysis.
\gd{Remark that Ethereum smart contracts enforce explicit declaration of accessed keys.}
Nonetheless, for transactions whose \fetch-es cannot be (accurately) predicted, the execution layer can always issue on-path \fetch to execute the transactions.
\sys supports all kinds of transactions with an additional optimization for common types of transactions.

The consequence of concurrent fetches is that the \fetch-ed values may be slightly stale and does not reflect the latest \bump operations (which may haven't been issue yet at the time of \fetch).
To address this, we introduce a bounded staleness semantic for \fetch.
The \fetch-ed value is allowed to be stale with respect to up to $s$ latest \bump operations, where $s$ is a system parameter.
When nodes retrieve the \fetch-ed values remotely, they accept the responses as long as their versions' staleness is within the bound and examine the responded values against the commitment of their corresponding versions.
This allows the remote nodes to respond to \fetch requests before advancing to the corresponding versions, effectively eliminating the sequential data dependency.
On the other hand, the execution layer takes care of only issuing up to $s$ concurrent fetches and further maintains a small in-memory cache of recent $s$ \bump operations.
When serving transaction reads, the cached updates supersede the \fetch-ed values if they overlap.
This cache not only guarantees to mask the staleness introduced by concurrent fetches but also potentially improves performance: if a hot key is frequently updated and fetched within a short period, the reads can be served directly from the cache and the performance is not affected by the \fetch at all.

\subsection{Archive Tier}

The active tier can achieve correctness and probabilistic availability with decent performance.
However, probabilistic availability may not be sufficient in some scenarios.
It is also vulnerable to a slowly adaptive adversary that can compromise nodes over time.\gd{cite}
To achieve deterministic availability, we introduce the archive tier.

The archive tier encodes the $f+1$ shards using erasure coding to produce $2f$ parity shards.
(This is why only $f+1$ shards are present in the active tier; the remaining ones are employed here.)
The $3f+1$ shards (including both original and parity shards) are stored on distinct nodes.
The encoding process ensures that at least $2f+1$ nodes participate, among which at least $f+1$ are correct.
The erasure code guarantees that any $f+1$ shards (original or parity) are sufficient to reconstruct the original $f+1$ shards.
Thus, the correct nodes involved in encoding always host enough shards to reconstruct the original data.

We now detail the encoding process.
Nodes first reach consensus on a specific version via atomic broadcast.
Once a node has brought its hosting shards to that version, it snapshots its stored shards and the commitments of non-hosting shards, and begins encoding, i.e., \emph{archiving} that version.
Nodes then exchange their snapshotted shards and verify correctness using the commitments.
To avoid loading the entire state into memory in this stage, the state can be divided into multiple stripes, each further divided into $f+1$ shards and managed as described above, with encoding performed stripe by stripe.
After collecting all $f+1$ shards, nodes independently encode them to produce $2f$ parity shards.
Finally, each node stores a hash vector of all shards and retains only one of the $3f+1$ shards according to its node index.
When reconstruction is needed, a node retrieves stored shards from all nodes and verifies their integrity using the hash vector.
As discussed, the node can always retrieve at least $f+1$ correct shards, ensuring successful reconstruction.
After encoding all stripes, nodes can discard the snapshotted shards and commitments.
The nodes can also perform garbage collection on both active and archive tiers up to the archived version, removing the unnecessary past values and archived shards.
Then, the nodes proceed to the next encoding round.

The archive tier and active tier complement each other.
The archive tier upgrades the availability guarantee of the active tier from probabilistic to deterministic.
The deterministic availability not only serves as an anchor point for garbage collection, but also effectively defends against a slowly adaptive adversary: as long as encoding occurs before the adversary compromises $f+1$ nodes, compromised nodes can only cause loss after the last archived version.
If such loss occurs, the system can recover by reconfiguring the active tier and re-executing transactions after the last archived version.

Meanwhile, the active tier provides correct shards to the archive tier for encoding and efficiently serves shards to the execution layer for transaction execution, while the archive tier handles the heavy encoding workload off the critical path of execution.

\subsection{Reasoning about Properties}

In the previous section, we focused primarily on the intuition behind the correctness and availability properties.
\gd{If necessary, add a formal proof sketch in the appendix?}
We now analyze the storage overhead.
For simplicity, we assume there is a single stripe in the following discussion, as each stripe is managed independently and the number of stripes does not affect the overall storage overhead.

The active tier stores $r$ replicas of each shard, totaling $r(f+1)$ shards.
The archive tier also stores $r(f+1)$ shards that are snapshotted for archiving.
Additionally, it stores $3f+1$ shards per archiving, and at most two rounds of archived shards may exist simultaneously, resulting in up to $2(3f+1)$ shards.
The sizes of commitments, past values, and hash vectors are negligible compared to the size of shards and are omitted from the analysis.

Therefore, the total number of shards stored in the system is at most $r(f+1) + r(f+1) + 2(3f+1) = (2r+6)f + 2r + 2$, for a state of size $f+1$ shards.
Thus, the aggregate storage overhead is
$$
\frac{(2r+6)f + 2r + 2}{f+1} < 2r + 6
$$
relative to the state size.
Since $r$ is a constant independent of the total number of nodes, we achieve storage scalability.
