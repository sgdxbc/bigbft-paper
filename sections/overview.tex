\section{Design}
\label{sec:overview}

\sys is a scalable key-value store that shards the key space into multiple partitions, stores each partition on a separate node shard, and tolerates Byzantine faults within each shard.
\sys can be dynamically reconfigured to add or remove node shards.
We omit the details of sharding scheme, reconfiguration, and state migration for simplicity, since many existing solutions are applicable given the consensus protocol employed by \sys.
\sys provides an interface similar to blockchains.
Clients submit transactions that call on-chain smart contracts, similar to stored procedures, executing which may read and write multiple keys.
\sys guarantees ACID properties.
All transactions submitted by correct clients will eventually be committed with atomic and serializable execution, and all reads return the values of the most recent writes to the corresponding keys.

\subsection{Design Overview}

\sys consists of three primary components: consensus, stateless transaction execution, and sharded state storage.
Every node in \sys is multiplexed across all three components.
The consensus component employs a BFT consensus protocol to accept transactions from clients and to order them globally.
The consensus protocol in \sys is not sharded: nodes across all shards participate in the same protocol.
When shards join or leave \sys, the consensus protocol is reconfigured to include additional or fewer nodes.
When there are $s$ shards, each with a disjoint set of $3f+1$ nodes where at most $f$ are Byzantine, the consensus protocol is configured to tolerate $sf$ Byzantine faults among a total of $s(3f+1)$ nodes, which is feasible because common consensus protocols can tolerate $sf$ Byzantine faults with at least $3sf+1$ nodes.
\sys can integrate any BFT consensus protocol as the consensus component;
those with scalable performance, such as DAG-based protocols~\cite{bullshark} and Autobahn~\cite{giridharan2024autobahn}, are preferred to avoid introducing scalability bottlenecks.
When using these protocols, clients can submit transactions to any node of any shard and commit transactions after receiving $sf+1$ matching confirmations from the nodes, ensuring at least one confirmation from a correct node.

The consensus component sequentially delivers blocks of transactions in a consistent order to the execution component, which executes the transactions and confirms to the clients after the writes are durably stored in the state storage component.
\sys adopts fully replicated execution: every node executes every transaction regardless of its shard, achieved through stateless execution.
When executing a block, a node fetches the read values from the state storage component and buffers the writes locally.
Although general transactions are supported, \sys favors transactions with read sets known in advance, which enables batched fetching of all transactions in the block and improves efficiency.
The node then posts the writes back to the state storage component and confirms to the clients after the post completes.

\subsection{State Storage and Access}

The state storage component exposes fetch and post interfaces to the execution component.
Like the node shards in Basil and sharded blockchains, in \sys the state storage component is sharded, and each shard is responsible for a disjoint partition of the key space.
Reads and writes are consistently directed to the corresponding shards via consistent hashing~\cite{karger1997consistent}.
Each fetch and post operation is divided into multiple network requests based on the accessed keys, and requests are sent to the corresponding shards in parallel.
This parallelism is key to enabling concurrent state access in \sys.

The state storage component handles fetch and post requests on a per-block basis.
For fetch requests, it simply returns the current values of the requested keys.
For post requests, it waits for $2sf+1$ matching requests from distinct nodes to ensure a quorum of correct nodes have posted, then applies the writes to the state, acknowledges all requests, and begins responding to fetch requests for the following blocks.
Because the consensus component is at the front, the state storage component in \sys is much simpler than Basil's shard replicas, since it effectively serves only one client: the execution component of the majority of correct nodes.
Therefore, it is designed as a simple data plane that does not need to handle concurrent or faulty clients.

In parallel, to fetch values from a state storage shard, the execution component sends fetch requests to all nodes in the shard and waits for $f+1$ matching responses to ensure at least one is from a correct node, thereby ensuring the integrity and freshness of the fetched values.
To post values to a state storage shard, the execution component sends post requests to all nodes in the shard and waits for $2f+1$ matching acknowledgments, ensuring that at least $f+1$ correct nodes have applied the writes and are ready to serve fetch requests for the following blocks, which is necessary for the liveness of subsequent fetches.

\subsection{Correctness and Liveness Proof}

We now sketch the correctness and liveness of \sys and defer the formal proof to the full version of the paper.
The atomicity and durability of transactions are guaranteed by the state machine replication mechanism, so we focus primarily on consistency, serializable isolation, and liveness.
The key insight is that the fetch and post operations served by the state storage component are always equivalent to having a full state copy on each node, as in normal BFT state machine replication, so the execution results are also equivalent to normal BFT systems, which are known to guarantee the desired properties.
Specifically, fetch and post operations always complete, and fetch operations always return the values of keys as they appear in the most recent posts containing those keys.

As described earlier, both the execution and state storage components wait for $f+1$ and $2f+1$ quorums of matching messages, respectively.
For each fetch request, the $f+1$ responding nodes must overlap with the $2f+1$ nodes that acknowledged the post request from which the fetched value originates, guaranteeing at least one correct node in the intersection and thus ensuring the correctness of the fetched value.
For liveness, post requests require only $2f+1$ acknowledgments, so $f$ Byzantine nodes cannot prevent them from completing.
Moreover, at least $f+1$ of those $2f+1$ acknowledgments must come from correct nodes, which will eventually respond to subsequent fetch requests for values in the posted updates, ensuring liveness of fetch operations.

We omit the discussion on garbage collection in this short paper.
Correct nodes that are slower than $2sf+1$ others may attempt to fetch a block after the state storage has already overwritten the fetch values with subsequent post updates.
In this case, the state storage component can respond with a certificate indicating that these nodes can safely skip executing the block, since at least $sf+1$ correct nodes must have executed the block and confirmed to the clients, ensuring the transactions committed.

\subsection{Optimizations}

% Optimal performance of \sys is achieved by minimizing state access overhead.
% \sys parallelizes state access by concurrently fetching and posting values to multiple shards in batches for each block, and we introduce several additional optimizations.

\paragraph{Caching.}
When state access happens locally, caching is widely deployed in multiple tiers of the system.
In \sys, while the state storage component can cache hot values locally, the execution component still pays the network overhead to access them.
Thus, the execution component is designed to cache recently accessed key-value pairs locally.
For workloads with highly skewed state access patterns, this cache can significantly reduce the number of keys to fetch for each block, bypassing the network for those accesses and achieving better performance.

\paragraph{Pipelining.}
In the design described above, only one of the execution and state storage components is active at a time: the execution component is idle while waiting for post acknowledgments, and the state storage component is idle while waiting for execution.
To further improve performance, we propose pipelining the execution and state storage components, while the consensus component is already pipelined to both.
While executing the current block, the execution component can concurrently post the writes of the previous block and fetch values for the next block.
At the same time, the state storage component serves fetch requests for the next block after the previous block's updates are posted instead of the current block's.
With this change, the state storage component responds to fetch requests with a fixed one-block staleness, so the execution component must maintain intermediate states between consecutive blocks to ensure execution correctness.

\paragraph{Trusted state access.}
Although logically separated, the three components are co-located on the same nodes, and components deployed on the same node share the same trusted domain.
We can leverage this trusted state storage component to remove quorum collection for a node's own shard.
When the execution component needs to fetch values from its own shard, it can directly access the local state storage component without sending network requests or waiting for multiple matching responses.
Similarly, when the state storage component receives post requests from the execution component on the same node, it can directly apply the writes without waiting for multiple matching requests.
