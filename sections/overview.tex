\section{System Design: An Iterative Refinement}
\label{sec:overview}

In this section, we detail the design of the state management system (SMS) within \sys.
As outlined in \autoref{sec:approach}, the execution layer provides the SMS with a consistent sequence of transactions across all correct nodes.
These transactions effectively transform the state into multi-versioned data, with each transaction generating a new state version.
The SMS is tasked with loading the necessary shards of the current state version to execute transactions, storing all versions of the shards that the nodes are responsible for maintaining, and responding to the load requests from other nodes.
\lijl{We should clearly define the SMS interface and its properties.}

The primary objective in designing the SMS is to guarantee two properties: storage scalability (\autoref{sec:bg}) and availability (\autoref{sec:approach}).
Storage scalability necessitates that the SMS stores only a bounded number of shards across all versions at any given time on each node.
Availability implies that every node can successfully load the shards it requires to update its view of the state to a newer version.
\lijl{The property definitions should be a bit more formal.}
It's important to note that to transition to a newer version, a node can either load shards of its current version and execute the intervening transaction, or, for nodes significantly behind a supermajority, directly load the shards of a more recent version and bypass the execution of the intermediate transactions \lijl{this sentence is not very clear}.
The latter approach requires the node to perform additional verification, which will be elaborated upon later.

For clarity, we will describe the design iteratively and analyze the desired properties at each stage.
We begin with a basic design, I1, then refine its redundancy level with I2. We subsequently merge I1 and I2 into a generational design, I3, to amortize the coding overhead. Finally, we combine a modified version of I1 with I2 to create I4, which offers improved usability.

\paragraph{I1: Sharding + Plain Replication.}
In the most basic design, consistent hashing~\cite{karger1997consistent} assigns each shard to $f+1$ nodes.
All shards are organized in a Merkle tree~\cite{merkle1987digital}, and nodes maintain inclusion proofs for the shards they store.
\lijl{Might want to briefly explain what a ``inclusion proof'' is and its property.}
The Merkle root represents the node's view of the whole state.
For each transaction, nodes load the necessary shards of their current state \lijl{it is not clear what does ``necessary shards of their current state'' mean}, process the transaction, update the Merkle root and the inclusion proofs of their stored shards, and advance the state version.
\lijl{For a new state version, does the shard assignment change due to consistent hashing?}
To load a shard, a node queries $f+1$ other nodes and waits for one reply with a valid inclusion proof.
The prior state versions (shards and proofs) are retained to serve later queries from potentially slower nodes.

Availability is straightforward: each version of every shard is hosted by $f+1$ nodes, ensuring at least one correct server.
Furthermore, all correct nodes maintain consistent views of each state version because they arrive at these versions by processing identical transaction sequences \lijl{and all loaded state shards are correct?}.
Consequently, an inclusion proof generated by one node can be verified by any other node, meaning a shard valid for its storing node is valid across the entire system.

\paragraph{Garbage Collection.}
I1 becomes practical only if historical versions of the shards can be pruned.
To enable this, we first modify I1 such that each shard is placed on $2f+1$ nodes instead of $f+1$.
This increased redundancy clearly does not compromise availability.

Next, upon bumping their state version (which can be implicitly signaled by querying shards of the subsequent version), nodes broadcast signed messages.
These messages include the node's Merkle root representing its view of that state version.
A $2f+1$ bump quorum (for a specific version) with matching Merkle roots serves as a certificate to garbage collect all (meta)data associated with versions prior to that \lijl{meaning both metadata and shard data?}.
Once a node gathers such a bump quorum certificate, it can prune its historical shards accordingly.

Reasoning on availability.
If $2f+1$ nodes have bumped up to a certain version, at least $f+1$ of them are correct.
For any given shard of that version, the $2f+1$ nodes responsible for serving it must overlap with these $f+1$ correct nodes by at least one correct node, which will serve the shard.
As the result, every shard of the \emph{highest} version certified by a bump quorum will be available.
Simultaneously, the bump quorum certificate also indicates the correct Merkle root (view of the state) for that version.
Therefore, it is safe to discard any older shard, because nodes requesting them can directly synchronize to that certified version and skip the intermediate execution, regardless of which specific shard(s) they require for that earlier version.

The liveness of garbage collection is straightforward, as the formation of a bump quorum only requires participation from all correct nodes.
During periods of synchrony, bump quorum certificates for increasingly newer versions will become available, and the garbage collection process will prune historical shards, allowing nodes to operate while storing a bounded number of shards.

\paragraph{I2: Erasure Coding.}
The I1 design incurs a redundancy of $2f+1$, which scales linearly with the number of potential faulty nodes. Consequently, I1 only compresses the storage consumption with a constant factor and fails to ensure storage scalability.

The refined design employs an EC$(k+2f,k)$ erasure code, as discussed in \autoref{sec:approach}.
To load a shard, a node queries the nodes storing the stripe to which the shard belongs and retrieves the \emph{entire} stripe.
Both the original data shards and the parity shards are incorporated into the Merkle tree \lijl{not immediately clear how this is done}, allowing nodes to verify the integrity of both.
After executing a transaction, the node reconstructs the parity shards for any stripe containing updated data shards (hence the need to load the entire stripe).
It then updates the Merkle root and the inclusion proofs for its stored state and parity shards, and then it bumps the state version, similar to I1.

Shard loading is always possible because out of the $k+2f$ queried nodes, at least $k+f$ are correct.
Since any $k$ correct nodes holding any $k$ pieces of the stripe (state or parity shards) can reconstruct the original $k$ data shards, the queried striped can always be reconstructed.
Furthermore, the garbage collection process still requires a bump quorum of only $2f+1$ participating nodes.
As mentioned in \autoref{sec:approach}, for each stripe, the $k+2f$ nodes responsible for serving it must overlap with this $2f+1$ quorum by at least $k$ correct nodes.
These $k$ correct nodes will possess enough state and parity shards to reconstruct the entire stripe.

\paragraph{Redundancy Analysis.}
The redundancy introduced by the EC$(k+2f,k)$ erasure code is $\frac{k+2f}{k}$.
When $k=1$, the redundancy becomes $2f+1$, which is equivalent to the plain replication design I1.
By setting $k=pf$, where $p$ is a constant in the range $(0,\frac{f+1}{f}]$, the redundancy becomes $\frac{pf+2f}{pf} = \frac{p+2}{p}$. This redundancy factor remains constant regardless of the state size and total storage capacity, thus achieving the desired storage scalability property.

However, this also implies that as $f$ increases (\ie, more nodes join the system), $k$ should ideally increase as well to maintain a target redundancy ratio.
This necessitates dynamically adjusting the number of shards within a stripe.

\paragraph{I3: Amortizing Erasure Code Overhead with a Generational Design.}
The I2 design involves frequent encoding and decoding operations, leading to two primary overheads.
First, although each parity shard is stored on only one node, every node must encode the original state shards to generate inclusion proofs for the state shards and parity shards it stores.
Second, while nodes can avoid decoding if all the shards within a queried stripe are successfully retrieved, this scenario only occurs when all $k$ original state shards of the stripe are stored by correct nodes.
Even if the $\frac{1}{3}$ faulty nodes employ no sophisticated strategy and simply withhold the shards they store, the probability that at least one required original state shard is stored and withheld by a faulty node is lower-bounded by $1-(\frac{2}{3})^k$.
This probability is undesirably significant and increases with $k$.

To effectively resolve this drawback, we adopt an epoch-based \emph{generational} approach.
New state versions are created in the \emph{young} generation, where shards are replicated on $f+1$ nodes, similar to the I1 design \lijl{it is not immediately clear that only shards that are modified by transactions are replicated}.
Periodically, the nodes transition into new \emph{epochs} and reach consensus on specific \emph{epoch versions} (through the consensus layer).
Once a bump quorum is achieved for an epoch version, the state corresponding to that epoch version is moved into the \emph{old} generation and encoded using the erasure code.
The redundant copies of the shards from the young generation can then be discarded.
Since all shard loading requests are served from the young generation, the encoding of the old generation can be performed in the background. This ensures that the process of loading shards is free from any encoding or decoding overhead.

The availability of I3 is guaranteed by the availability properties of both I1 and I2.
Initially, the young generation seems to introduce an $f+1$ redundancy (as in I1), potentially undermining the storage scalability objective.
However, these $f+1$ shard copies are only maintained for the shards that are updated within the current epoch.
In many real-world applications, workloads exhibit high skewness, and the size of the frequently accessed ``working set'' of data tends to be bounded and independent of the total state size.
Nevertheless, this approach might not be optimal for all workload patterns, and malicious nodes could still execute withholding attacks at the beginning of each epoch, affecting performance.
This limitation is addressed in the subsequent design.

\paragraph{I4: Achieving Constant Redundancy with Probabilistic (Fast Path) Availability.}
In this design, we capitalize on the fact that the archive layer can solely ensure robust availability on its own.
And we introduce a \emph{relaxed} availability guarantee for the active layer.
Drawing inspiration from \cite{qi2020bft}\footnote{Their work focuses on the availability of blocks rather than state, as discussed in \autoref{sec:rel}.}, we repurpose the young generation as a fast path with probabilistic availability.
Instead of maintaining $f+1$ replicas, the young generation stores a fixed number $c$ of copies for each shard, distributed across uniformly random nodes, irrespective of $f$.
Moreover, the young generation retains copies of \emph{all} active shards, representing the latest version of every shard, even if that version has also been moved to the old generation.
Thus, we henceforth refer to the young and old generations as the \emph{active} and \emph{archive} layers, respectively.

The archive layer ultimately guarantees the availability of the last archived version of the state, as detailed in the I2 design.
The availability of every stripe (and thus every shard) of any version can be ensured by replaying the transactions starting from the last archived version.
Furthermore, the probability of each shard being available from the active layer is $1-(\frac{2}{3})^c$, which exceeds 99.9\% with $c=7$ and surpasses six-nines with $c=13$.
The resilience of the active layer grows exponentially with $c$ and is configurable by the administrator.
Crucially, a potential failure of the active layer does not transform \sys into a speculative BFT protocol and does not necessitate rollback capabilities in the replicated state machine. In the recovery scenario where shards are unavailable in the active layer, the transaction history remains intact, and nodes simply re-execute the same sequence of transactions assisted by the archive layer.
Any replies already committed to clients will not be invalidated.
Finally, the storage overhead of the active layer is $c$ times the state size, independent of the number of nodes, and the archive layer achieves storage scalability, as discussed in I2.
Therefore, I4 is a design that effectively achieves both availability and storage scalability.
