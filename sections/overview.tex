\subsection{System Architecture}

The participants are logically divided into two types of nodes: \emph{replica nodes} and \emph{storage nodes}.
Each participant operates one replica node and one storage node.
The replica nodes operate a Byzantine atomic broadcast protocol to agree on the order of transactions and two storage signals: checkpoint and reconfigure.
They also execute all transactions in the agreed order.
On each checkpoint signal, a specific version of the state is snapshotted and collectively stored on the storage nodes.
The replica nodes maintain the updates since the last checkpoint locally, and retrieve the missing state from the storage nodes when necessary.
The storage nodes determine the part of the state they store according to a hybrid scheme consisting of randomized replication and erasure coding.
They serve the retrieval requests with the replication and recover the state with the erasure coding when the replication fails.

\subsection{Storing Format}

The state is divided into certain number of \emph{shards}, each of which is independently checkpointed, managed and reconstructed.
Each shard is a key-value map.
The stored value of each key is a tuple consisting of the actual value, the successor key according to lexicographic order, and an aggregated signature from $f+1$ replica nodes signed over the key, actual value, successor key and the checkpoint version.
When retrieving values from the storage nodes, the replica nodes can verify the signatures with the aggregated public keys of the replica nodes.
If the signature is valid, the replica nodes are assured that at least one correct replica node has endorsed the value and can accept it.
To prove the non-existence of a key, the storage nodes return the values of its predecessor, which contains the successor key showing the absence of the requested key.

\subsection{Checkpoint and Reconfigure}

The storage nodes periodically vote for checkpoint via atomic broadcast, and a new checkpoint signal is triggered after receiving $2f+1$ votes.
For each checkpoint, the storage nodes first send the previously checkpointed shard to the replica nodes
The replica nodes then flush the updates since the last checkpoint into the shard and construct their \emph{shard shares} for the new checkpoint with the updated successor keys, checkpoint version and their signature shares.
The replica nodes send their shard shares to all storage nodes.
Each storage node collects matching shard shares from $f+1$ replica nodes, aggregate the signature shares into signatures and construct the shard for checkpointing.

Each shard is stored on the storage nodes in two forms simultaneously: it is replicated on $r$ random storage nodes for retrieval and also distributed among all storage nodes with a $RS(3f+1, f+1)$ erasure code for reconstruction.
The $r$ full copies ensure the shard can be retrieved with high probability: the probability that all $r$ nodes storing the full copies of a shard are faulty is $(\frac{f}{3f+1})^r$, which decreases exponentially with $r$.
To achieve storage scalability, $r$ is a constant independent of the total number of storage nodes and may be less than $f$.
On the other hand, the erasure coding deterministically ensures that the shard can be reconstructed as long as no more than $f$ nodes are faulty.
There are at least $2f+1$ nodes participating in checkpointing, among which at least $f+1$ are correct nodes.
These $f+1$ correct nodes store distinct chunks of the shard, which are sufficient to reconstruct the original shard.

To retrieve a value of a key, the replica nodes contact the $r$ storage nodes responsible for the shard containing the key.
The replica nodes verify the retrieved value as described above and return the first correct response.
If all $r$ nodes are faulty, the retrieval may stall.
In such case, the replica nodes vote to trigger a reconfigure signal via atomic broadcast.
The reconfigure signal provides a random seed, according to which the $r$ random storage nodes storing the full copies of each shard are re-selected.
The storage nodes then exchange the encoded chunks of the last checkpointed shards and verify their integrity using the stored hashes.
Then, they reconstruct the original shards and store full copies of them according to the new shard placement.
After reconfiguration is done, the replica nodes can retry the stalled retrieval request with another set of $r$ storage nodes.

\subsection{Garbage Collection}

After a new checkpoint is created, the storage nodes can safely delete the data of the previous checkpoint.
The last checkpointed version corresponds to the lowest alive version in \autoref{sec:approach}, i.e., at least $2f+1$ replica nodes have passed this version, or the checkpoint cannot be created yet.
If a replica node observes that a new checkpoint has been created (via $2f+1$ checkpoint votes for the next checkpoint) for the version later than its local execution version, it can conclude that it has fallen behind the lowest alive version and \forward to it.

\subsection{Reasoning about Properties}

In the previous sections, we focused primarily on the intuition behind the correctness and availability properties.
\gd{If necessary, add a formal proof sketch in the appendix?}
We now analyze the storage overhead.
For simplicity, we analyze the storage overhead from the perspective of a single shard, as the shards are independent and identical in design.
We also only consider the storage overhead of checkpoints, as the other data (e.g., updates since last checkpoint, encoded chunk hashes) are negligible and reside in memory.

Each shard is replicated on $r$ storage nodes and also encoded into $3f+1$ chunks with a $RS(3f+1, f+1)$ erasure code.
The replication contributes a storage overhead of $r$ times, and the erasure coding contributes a storage overhead of $\frac{3f+1}{f+1} < 3$ times.
There are at most two checkpoints stored on the storage nodes at any time.
Therefore, the total storage overhead per shard is less than $2(r+3)$ times.
