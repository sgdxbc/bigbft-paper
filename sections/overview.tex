\section{System Design}
\label{sec:overview}

\subsection{Active Tier}

Firstly, we describe a simplified version of the active tier.
The key space is divided into $f+1$ shards, each of which is stored on a distinct node.
(We will later explain why not using $3f+1$ shards.)
For each of the shards, the hosting node accesses the shard locally, while the other $3f$ nodes retrieve the values of the accessed keys from the hosting node.
After executing a transaction, the hosting node updates the values of the stored shard, while the other nodes simply discard the retrieved values.
Remarks that the hosting node stores not only the current shard, but also the values of the accessed keys of the past transactions, so that a node that is running behind can still retrieve the necessary values to execute.
We will discuss when the past values can be garbage collected later.

To ensure the correctness of the active tier, the $3f$ nodes must be able to verify the correctness (i.e., integrity and freshness) of the retrieved values.
We employ the \emph{accumulator} to achieve this.
An accumulator, or a updatable vector commitment, is a cryptographic primitive that allows one to succinctly represent a set of values and efficiently prove the inclusion of a value in the set.
In our design, the $3f$ nodes maintain the accumulator of the shard.
When they retrieve the values of some keys from the hosting node, the hosting node also provides the inclusion proofs of those keys in the accumulator.
At the same time, the accumulator supports efficient updates.
When the values of some keys are updated in the shard due to the execution of a transaction, the retrieving nodes can require necessary information from the hosting node to update their local copy of the accumulator.
The update scheme ensures that the accumulator is always consistent on the retrieving nodes.

In conclusion, the accumulator allows the retrieving nodes to \emph{attest} the correctness of the retrieved values and reject the incorrect ones independently.

To ensure the availability of the shard, we replicate each shard on $r$ random nodes.
To ensure storage scalability, $r$ is a constant independent of the total number of nodes and may be less than $f$.
While there is a chance that all $r$ nodes storing a shard are faulty, we randomize the placement of shards.
So, a key (and the shard it belongs to) is stored by $r$ nodes, each of which is faulty with a probability of $\frac{f}{3f+1}$ independently.
As the result, the probability that all $r$ nodes storing a shard are faulty is $(\frac{f}{3f+1})^r$, which decreases exponentially with $r$, regardless of the total number of nodes.
Thus, the probabilistic availability of each shard can be ensured with a sufficiently large $r$.
This guarantee is sufficient in some practice, and we will later describe how to achieve deterministic availability.

\paragraph{Garbage collection of past values.}
As previously mentioned, the hosting node stores not only the current shard but also the values of the accessed keys of the past transactions.
The number of past transactions that the node can host must be bounded to ensure storage scalability.
So the past values must be garbage collected in a timely manner.
If the garbage collection is not happening in time, the node must suspend the execution of new transactions to avoid the need of storing more past values.

To ensure the liveness of garbage collection, the past values are collected after $2f+1$ nodes have executed the corresponding transaction.
The nodes exchange signed messages that indicate the transaction sequence number they have executed (which can be implied by their retrieving requests).
Once a node receives $2f+1$ messages indicating that they have executed a transaction, it can safely discard the past values accessed by that transaction.
On the other hand, if the execution on that node is fetching or bumping for the transaction earlier than the quorum-executed transaction, the fetching or bumping may not be able to be resolved because the past values have been discarded.
In this case, the node can skip the execution of the transaction and fast-forward to the quorum-executed transaction.
This is acceptable by all the BFT protocols we are aware of, as any BFT protocol that requires more than $2f+1$ nodes to execute a transaction cannot ensure liveness anyway.

To mitigate the latency and throughput penalty introduced by the on-path retrieval discussed in \autoref{sec:approach}, we can prefetch the values of keys that are likely to be accessed by future transactions.
For stored procedure, we can usually perfectly predict the keys that will be accessed by a transaction.

However, during the interval of prefetching and execution, the values of the prefetched keys may be updated by other transactions.
Nodes must locally keep track of the updates made by a certain number of the most recent transactions, and the number is determined by the number of transactions that can be prefetched ahead.

\subsection{Archive Tier}

The active tier can achieve correctness and probabilistic availability with decent performance.
However, the probabilistic availability may not be sufficient in some practice.
It is also vunerable to slowly adaptive adversary that can compromise nodes over time.\gd{cite}
To achieve deterministic availability, we introduce the archive tier.

The archive tier encodes the $f+1$ shards with an erasure code and produces $2f$ parity shards.
(This is why we have $f+1$ shards instead of $3f+1$ shards in the active tier.)
The $3f+1$ shards (including the original and parity shards) are stored on all of the $3f+1$ nodes.
The encoding routine ensures that at least $2f+1$ nodes have participated, among which at least $f+1$ are correct.
The erasure code guarantees that any $f+1$ shards (original or parity) are sufficient to reconstruct the original $f+1$ shards.
So the correct nodes who have participated in the encoding can always reconstruct the original shards and serve them to the system.

We now detail the encoding routine.
The nodes first reach consensus on a certain transaction sequence number through the atomic broadcast.
Once a node has executed all transactions up to that sequence number, it snapshots its storing shards and starts to work on the encoding, i.e., \emph{archiving} that sequence number.
The nodes then exchange their snapshoted shards and verify their correctness with the accumulators provided by the active tier (which are also snapshoted).
To avoid loading the entire shards into memory in this stage, the whole state can be divided into many stripes, and each stripe is further divided into $f+1$ shards and managed as described previously, and the encoding is performed on one stripe by another.
After the nodes collect all the $f+1$ shards, they independently encode the shards to produce $2f$ parity shards.
Finally, they store a hash vector of all the shards and only one of the $3f+1$ shards according to their node indices.
Later when a node needs to reconstruct the original shards, it retrieves the stored shards from all nodes and verifies their integrity with the stored hash values.
After they encode all the stripes, the nodes can discard the snapshoted shards and accumulators, and the archived shards from the previous encoding.
Then the nodes can start a new round of encoding.

The archive tier and the active tier complement each other.
The archive tier strengthens the availability guarantee of the active tier from probabilistic to deterministic, and it can effectively defend against slowly adaptive adversary: as long as the encoding is performed before the adversary can compromise $f+1$ nodes, the compromised nodes can only cause the loss after the last archived sequence number.
And if that happens, the system can recover by reconfiguring the active tier and re-executing the transactions after the last archived sequence number.

On the other hand, the active tier serves the shards to the archive tier for encoding, and it also efficiently serves the shards to the execution layer for transaction execution, while the archive tier deals with the heavy encoding workload which should be performed off the critical path of execution.
