\section{Decoupling State from Execute}
\label{sec:approach}

From the previous works of all of fully replicated blockchains, sharded blockchains and stateless blockchains, we observe a common theme: the nodes store what they need to execute the transactions on their own.
In another word, what nodes can (and will) execute is determined by what state they store locally.
In fully replicated blockchains, all the nodes maintain the entire state and execute all transactions.
In sharded blockchains, the nodes only need to maintain a state shard because they only execute transactions that access that shard.
In stateless blockchains, the internal nodes do not maintain the state because they don't (also cannot) execute transactions.
While the external storage nodes maintain the entire or part of the state and execute the transactions whose execution can be supported by the state they maintain.

This ``store what you need for execution'' common theme leads to the dilemma between storage scalability and security guarantees.
On one hand, storage scalability cannot be achieved if the state is replicated to all nodes or a set of nodes whose size is proportional to the total number of nodes.
That means that for each transaction, the state it accesses can only be stored on a limited set of nodes whose number is independent of the total number of nodes.
In only the nodes storing the accessed state can (and will) execute the transaction, the number of executing nodes is limited as well.
However, the conventional security guarantees of blockchains, i.e., safety and liveness, can only be achieved when a transaction is executed by all nodes\gd{cite 3f+1 lower bound here}.
This fundamental theoretical limitation forces the sharded and stateless blockchains to trade the security guarantees in various ways (\autoref{sec:bg}) for storage scalability.

If we diverge from this common practice, the chance of achieving both storage scalability and security guarantees appears.
As shown in \autoref{fig:approach-compare}, we propose a novel design that decouples state management from transaction execution.
In this design, the nodes execute all transactions while only maintaining a part of the state, i.e., one or more state shards.
If a transaction accesses a state shard that is not stored locally, the node retrieves it from other nodes to execute the transaction.
By carefully engineering the state placement, we can ensure that each shard is stored on a limited set of nodes, achieving storage scalability.
At the same time, since all nodes execute all transactions, the security guarantees are preserved as well.

\paragraph{The size of the retrieved temporary state.}
One obvious concern of this design is that the worst case size of the retrieved temporary state could be as large as the entire state, for example, if a transaction accesses all state shards.
We remark that this is a theoretical worst case that is unlikely to happen in practice.
In practice, most transactions only access a tiny fraction of the state.

For example, in Ethereum, more than 90\% of transactions only access a single account.
Also, as we will show in our design, the retrieval happens at key level, so that even if a transaction accesses keys that are stored by many or even all nodes, those nodes only transfer the values of the accessed keys instead of the entire shards they store.
So the peak size of the retrieved temporary state is equal to the size of the accessed keys and values, which is small enough to even only reside in memory.

However, diverging from the common practice also gives up its benefits: execute with local state is efficient and does not require additional security reasoning.
As the state is maintained by the node itself, the state is always correct and available to the node, and the execution of the same sequence of transactions on the same initial state will always halt with the same final state and output.
As the result, the previous sharded and stateless blockchains can mostly focus on establishing the consistent ordering of transactions to ensure their security guarantees.
On the other hand, our design of decoupling state from execution introduces new challenges to ensure the correctness and availability of the state shards retrieved from other nodes, which are crucial for the security guarantees.
If the nodes retrieves incorrect values, the execution may diverge.
If the retrieval does not complete, the execution is stuck.
Even if the retrieval do complete but just not efficiently, the execution will be delayed and the throughput will be reduced.
We will detail these challenges below and outline our approaches to address them in \autoref{sec:overview}, but before that, we first formalize the interfaces and the security properties of the state management.

\subsection{Interfaces and Security Properties of State Management}

In our design, the BFT protocol consist of three components: the state management system (SMS), the execution layer and the Byzantine atomic broadcast (BAB) protocol.
We specify the design of the SMS and the execution layer, while the Byzantine atomic broadcast protocol can be any existing protocol that satisfies the standard properties (validity, agreement, integrity and total order)\gd{cite here}.
In this section, we first define the universal interfaces for state management to abstract away the implementation details and describe the overall workflow of the proposed BFT protocol.
Then we define the security properties that the state management must satisfy to ensure the security guarantees of the overall system.
Finally, we reason about how the overall security properties are preserved given that the SMS and BAB ensure their own properties and the transaction execution is deterministic.

We take a key-value view of the state: the state is a mapping from keys to values, and each transaction accesses a set of keys to read or write their values.
This view is compatible with most blockchain applications, including account-based model and UTXO-based model.

The interfaces of the SMS are defined as two operations: \fetch and \bump.
Normally, \fetch($k$) outputs the value associated with the key $k$, and \bump($[k_1 \mapsto v_1, k_2 \mapsto v_2, \ldots]$) updates the values associated with the keys $k_i$ to $v_i$ and outputs \texttt{OK}.
The execution layer is straightforward with these two operations and the BAB protocol.
Upon receiving transactions from the clients, the BAB protocol establishes a total order of the transactions and delivers them to the execution layer.
During executing transactions, the execution layer gradually \fetch all keys as the execution requires reading, and buffers all key-value pairs written by the execution.
When the execution finishes for the transactions, the execution layer \bump all buffered key-value pairs to update the state, and responds to clients with the execution results.
The clients collect $f+1$ identical responses from distinct nodes before concluding the transaction is committed.
In the special case where the node lags behind and needs to catch up, \fetch and \bump may output \forward($s$), indicating that the node should skip the following $s$ \bump calls and any \fetch calls in between.
(The case of leveraging \forward is shown in the garbage collection design in \autoref{sec:overview}.)
In the view of the execution layer, this simply translates to skipping the execution of the next $s$ transactions (including the current one).
The SMS guarantees to only output \forward when there are at least $2f+1$ nodes have already executed and \bump the corresponding transactions.
As shown later, this is sufficient to ensure the liveness of the overall BFT protocol.

The straw-man implementation of the SMS is to fully store the entire state on the node and implement \fetch and \bump as local operations on the local state (and they never outputs \forward).
In \sys, we design a distributed implementation of the SMS that is storage scalable.
Next, we define the security properties of SMS that captures the essential assumptions made by the execution layer to a local SMS: correctness and availability.
By ensuring these properties, an SMS implementation would ``behave as'' a local one to the remaining system, so that as long as the system can ensure its security properties with a local SMS, it can ensure the same properties with this SMS implementation as well.

\paragraph{State version.}
For clearness, we define the \emph{version} of the state as the number of transactions that ought to be executed, i.e., the number of \bump calls that have been executed plus the number of \bump calls that have been \forward-ed.

\paragraph{Assumptions made by the SMS\@.}
SMS may assume a consistent sequence of \fetch and \bump calls from the execution layer.
Specifically, at each version, the nodes receive identical \fetch and \bump calls.

\paragraph{Correctness.}
The value outputs by \fetch($k$) must match the last \bump call that updates $k$. 
\gd{A weaker property that only requires returning consistent values is probably sufficient, but this definition seems more reasonable.}

\paragraph{Availability.}
Each \fetch and \bump call must eventually output, and for each version, \fetch and \bump calls may output \forward on at most $f$ nodes.
\gd{A bit attempting to extract the latter part into a ``quorum progress'' property.}

Given that the SMS ensures these properties, the BAB protocol ensures its standard properties and the transaction execution is deterministic, we now show that the overall system can ensure the conventional safety and liveness properties of BFT protocols regardless of the implementation of the SMS\@.
The BAB protocol ensures that the execution layer of all non-faulty nodes receive the same sequence of transactions.
Because of deterministic execution, the execution layer of all non-faulty nodes will translate the transaction executions into the same sequence of \fetch and \bump calls, satisfying SMS's assumptions.
Then, the availability of SMS ensures that all non-faulty nodes can proceed to every state version (by either execution or \forward over it), and at least $2f+1$ nodes
who proceed a version have executed the corresponding transaction (instead of \forward over it).
Combining both statements gives that for each version, at least $f+1$ non-faulty nodes have executed the corresponding transaction.
Finally, the correctness ensures that as long as the executions start from consistent pre-states, the executions yield consistent results and transition into consistent post-states.
Given that all nodes start from the same initial state, by induction, all non-faulty nodes will yield consistent results for all transactions they have executed.
As the result, for each transaction, the client can collect $f+1$ identical responses from the executing non-faulty nodes, satisfying the safety and liveness properties of BFT protocols.

\subsection{Challenges}
Ensuring availability is challenging.
If a state shard is stored only on the faulty nodes, the shard can be lost.
However, if we store each shard on at least $f+1$ nodes to ensure it is not only stored on the faulty nodes, the storage overhead is proportional to the number of nodes, losing storage scalability.

Ensuring correctness is also challenging.
As the system consists of up to $f$ faulty nodes, those nodes may attempt to respond to retrieval requests with malformed or stale data.
The retrieving node must be able to detect and discard such incorrect data to avoid execution divergence.
The straightforward solution is to collect $f+1$ identical responses from distinct nodes, ensuring at least one correct response.
However, this approach requires storing each shard on at least $2f+1$ nodes, which again results in storage overhead proportional to the number of nodes.

Last but not least, the retrieval of state shards from other nodes introduces additional network traffic, and more importantly, on the critical path of execution.
While waiting for the retrieval, the execution is blocked, and the node cannot execute any other transaction in the meanwhile because the execution must be sequential to ensure consistency.
This results in not only increased latency but also reduced throughput because of the degraded node utilization.
