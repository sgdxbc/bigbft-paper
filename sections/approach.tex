\section{Decoupling State from Execute}
\label{sec:approach}

From the previous works of all of fully replicated blockchains, sharded blockchains and stateless blockchains, we observe a common theme: the nodes maintain the part of the state (or the whole state) necessitated by the transactions they execute all by themselves.
In fully replicated blockchains, all the nodes execute all transactions and maintain the entire state.
In sharded blockchains, the nodes only need to maintain a state shard because they only execute transactions that access that shard.
In stateless blockchains, the internal nodes do not maintain the state because they don't (also cannot) execute transactions.
While the external storage nodes maintain the entire or part of the state and execute the transactions whose execution can be supported by the state they maintain.

This common theme leads to the dilemma between storage scalability and security guarantees.
On one hand, storage scalability cannot be achieved if the state is replicated to all nodes or a set of nodes whose size is proportional to the total number of nodes.
That means that for each transaction, the state it accesses can only be stored on a limited set of nodes whose number is independent of the total number of nodes.
In only the nodes storing the accessed state can (and will) execute the transaction, the number of executing nodes is limited as well.
However, the conventional security guarantees of blockchains, i.e., safety and liveness, can only be achieved when a transaction is executed by all nodes\gd{cite 3f+1 lower bound here}.
This fundamental theoretical limitation forces the sharded and stateless blockchains to trade the security guarantees in various ways (\autoref{sec:bg}) for storage scalability.

If we diverge from the common practice of executing the transaction only if the local state can support the execution, we can achieve both storage scalability and security guarantees.
As shown in \autoref{fig:approach-compare}, we propose a novel design that decouples state management from transaction execution.
In this design, the nodes execute all transactions while only maintaining a part of the state.
If a transaction accesses a state shard that is not stored locally, the node retrieves it from other nodes to execute the transaction.
By carefully engineering the state placement, we can ensure that each shard is stored on a limited set of nodes, achieving storage scalability.
At the same time, since all nodes execute all transactions, the security guarantees are preserved as well.

\paragraph{The size of the retrieved temporary state.}
One obvious concern of this design is that the worst case size of the retrieved temporary state could be as large as the entire state, for example, if a transaction accesses all state shards.
We remark that this is a theoretical worst case that is unlikely to happen in practice.
In practice, most transactions only access a tiny fraction of the state.
\gd{Copilot believes the following sentence, try to cite it or remove if not found.}
For example, in Ethereum, more than 90\% of transactions only access a single account.
As we will show in our design, the retrieval happens at key level, so that even if a transaction accesses keys that are stored by many or even all nodes, those nodes only transfer the values of the accessed keys instead of the entire shards they store.
So the peak size of the retrieved temporary state is equal to the size of the accessed keys and values, which is small enough to even only reside in memory.
\gd{In some way claim that this is also what blockchains like Ethereum are doing and assuming.}

However, the common practice of maintaining the state necessary for executing transactions locally comes with its reason: execute with local state is efficient and does not require additional security reasoning.
As the state is maintained by the node itself, the state is always correct and available to the node, and the execution of the same sequence of transactions on the same initial state will always halt with the same final state and output.
As the result, the previous sharded and stateless blockchains can mostly focus on establishing the consistent ordering of transactions to ensure their security guarantees.
On the other hand, our design of decoupling state from execution introduces new challenges to ensure the correctness and availability of the state shards retrieved from other nodes, which are crucial for the security guarantees.
We will detail these challenges and outline our approaches to address them, but first we formalize the interfaces and the security properties of the state management.

\subsection{Security Properties of State Management}

Interfaces: fetch and bump.

Properties: availability and correctness.
In essence, fetch and bump behaves as the node locally stores everything (except the forwarding).

\subsection{Challenges}
Ensuring availability is challenging.
If a state shard is stored only on the faulty nodes, the shard can be lost.
However, if we store each shard on at least $f+1$ nodes to ensure it is not only stored on the faulty nodes, the storage overhead is proportional to the number of nodes, losing storage scalability.

Ensuring correctness is also challenging.
As the system consists of up to $f$ faulty nodes, those nodes may attempt to respond to retrieval requests with malformed or stale data.
The retrieving node must be able to detect and discard such incorrect data to avoid execution divergence.
The most straightforward solution is to collect $f+1$ identical responses from distinct nodes, ensuring at least one correct response.
However, this approach requires storing each shard on at least $2f+1$ nodes, which again results in storage overhead proportional to the number of nodes.

Last but not least, the retrieval of state shards from other nodes introduces additional network traffic, and more importantly, on the critical path of execution.
While waiting for the retrieval, the execution is blocked, and the node cannot execute any other transaction in the meanwhile because the execution must be sequential to ensure consistency.
This results in not only increased latency but also reduced throughput because of the degraded node utilization.
