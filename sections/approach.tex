\section{Decoupling State from Execute}
\label{sec:approach}

From prior research on fully replicated blockchains, sharded blockchains, and stateless blockchains, we observe a common principle: nodes store the state necessary to execute transactions independently.
In other words, the set of transactions a node can execute is determined by the state it maintains locally.
In fully replicated blockchains, every node maintains the complete state and executes all transactions.
In sharded blockchains, nodes only maintain a shard of the state, as they execute transactions that access that shard.
In stateless blockchains, internal nodes do not maintain state because they neither execute nor are able to execute transactions.
Instead, external storage nodes maintain all or part of the state and execute those transactions that can be supported by the state they store.

This ``store what you need for execution'' common theme leads to the dilemma between storage scalability and security guarantees.
On one hand, storage scalability cannot be achieved if the state is replicated to all nodes or a set of nodes whose size is proportional to the total number of nodes.
That means that for each transaction, the state it accesses can only be stored on a limited set of nodes whose number is independent of the total number of nodes.
If only the nodes storing the accessed state can execute the transaction, the number of executing nodes is also limited.
As the number of $f$ faulty nodes increases with the total number of nodes, the faulty nodes can eventually outnumber the executing nodes, making it impossible to achieve security guarantees (without seeking unconventional extensions to the security model).
This fundamental theoretical limitation forces sharded and stateless blockchains to trade off security guarantees in various ways (\autoref{sec:bg}) in exchange for storage scalability.
\lijl{We can probably frame this into an informal impossibility result. That is, a system can choose at most one of the two properties. Then informally ``prove'' that if security is chosen, then storage scalability can't be achieved, and vice versa.}

Diverging from this common practice, we propose to \emph{decouple state from execution}.
Each transaction is executed by \emph{all} nodes, regardless of the state they maintain.
The nodes are allowed to maintain only a portion of the state or even no state at all.

Traditional approaches are pessimistic: a node needs to always maintain all state. This is an overkill for execution. We are doing is on-demand or optimistically.} \gd{Done with next sentence.}
We exploit the fact that while the entire state is necessary to execute all possible transactions, each \emph{individual} transaction may not access the entire state, and most transactions in practice access only a small portion of the state.
When executing a transaction, if a node needs to access state that it does not maintain locally, it retrieves the required state from other nodes to complete the execution.
With this state-execution decoupling, we can independently design state management to achieve storage scalability, while all nodes execute all transactions to retain security guarantees.
\lijl{Can relate to other systems designs, e.g., memory is separated from CPU execution logic (CPU only maintains registers and caches), prior disaggregated memory.}
If a transaction accesses a state shard not stored locally, the node retrieves it from other nodes to complete the execution.
By carefully designing the placement of state shards, we ensure that each shard is stored on a limited subset of nodes, thereby achieving storage scalability.

A natural concern with this design is that, in the worst case, the size of the retrieved temporary state could be as large as the entire state, for instance, if the transactions scan the entire state. 
We emphasize that this is a theoretical worst case and is unlikely to occur in practice.
Empirically, most transactions access only an extremely small fraction of the state.

\subsection{The Dual Node Architecture for State-execution Decoupling}

Following the state-execution decoupling principle, we propose a dual node architecture where each participant a \emph{replica node} and zero or more \emph{storage nodes}, depicted in \autoref{fig:approach-compare}.
The replica node is similar to a traditional BFT node: it contributes to consensus and executes all transactions.
However, it does not maintain the execution state.
Instead, it is accessible to the interfaces of the \emph{state management system} (SMS), which allow it to read and write state as needed during transaction execution, as if it were maintaining the state locally.
The SMS consists of the storage nodes of all participants.
Behind the scenes, the SMS interfaces retrieve and push the state from and to the storage nodes as required.
We will detail the SMS interfaces and their security properties in the next section.

In this work, we examine the canonical BFT setting, where each participant operates one replica node and one storage node.
This configuration is sufficient to the goal of achieving storage scalability under a conventional BFT security model.
However, the dual node architecture is flexible and can accommodate various configurations.
\sys can tolerate up to $f$ participants that host at most $k$ storage nodes totally with $3f+1$ participants hosting at least $3k+1$ storage nodes in total.
This flexibility is especially beneficial in permissionless settings, where participants may have heterogeneous storage capacities.
In such systems, the powerful participants can be incentivized to host multiple storage nodes to enhance the overall storage capacity of the system, while each participant only needs to operate one replica node to contribute to consensus and execution.
As the result, the powerful participants can make profit from their storage capacities that are potentially even larger than the state size, while the less powerful participants can still participate in consensus and execution without being burdened by storage requirements, maximizing the decentralization of the system.

\subsection{Interfaces and Security Properties of State Management}

In our design, the BFT protocol consists of three components: the state management system (SMS), the execution layer, and the Byzantine atomic broadcast (BAB) protocol.
We specify the design of the SMS and the execution layer, while the BAB protocol can be any existing protocol that satisfies the standard properties (validity, agreement, integrity, and total order)~\gd{cite here}.
In this section, we first define universal interfaces for state management to abstract away implementation details and describe the overall workflow of the proposed BFT protocol.
Next, we define the security properties that state management must satisfy to ensure the security guarantees of the overall system.
Finally, we reason about how the overall security properties are preserved, given that the SMS and BAB ensure their respective properties and transaction execution is deterministic.

We adopt a key-value abstraction for the state: the state is represented as a mapping from keys to values, and each transaction accesses a set of keys to read or write their associated values.
This abstraction is compatible with most blockchain applications, including both account-based and UTXO-based models.
\lijl{Can also mention that most distributed databases use such storage interface.}

The interfaces of the SMS are defined as two operations: \fetch and \bump.
Typically, \fetch($k$) returns the value associated with key $k$, and \bump($[k_1 \mapsto v_1, k_2 \mapsto v_2, \ldots]$) updates the values of keys $k_i$ to $v_i$ and returns \texttt{OK}.
The execution layer operates straightforwardly with these two operations and the BAB protocol.
Upon receiving transactions from clients, the BAB protocol establishes a total order of transactions and delivers them to the execution layer.
During transaction execution, the execution layer incrementally invokes \fetch for all required keys and buffers all key-value pairs written by the execution.
After execution completes for the transactions, the execution layer calls \bump on all buffered key-value pairs to update the state and responds to clients with the execution results.

Clients collect $f+1$ identical responses from distinct nodes before considering the transaction committed.
In the special case where a node lags behind and needs to catch up, \fetch and \bump may return \forward($s$), indicating that the node should skip the next $s$ \bump calls and any \fetch calls in between.
(The use of \forward is illustrated in the garbage collection design in \autoref{sec:overview}.)

The SMS guarantees to output \forward only when at least $2f+1$ nodes have already executed and \bump-ed the corresponding transactions.

The straw-man implementation of the SMS is to store the entire state locally and implement \fetch and \bump as local operations, which never output \forward.
In \sys, we design a distributed SMS implementation that achieves storage scalability.
Next, we define the security properties of SMS that capture the essential assumptions made by the execution layer about a local SMS: correctness and availability.
By ensuring these properties, an SMS implementation can behave equivalently to a local one for the rest of the system, so that if the system can guarantee its security properties with a local SMS, it can guarantee the same properties with this SMS implementation.

Given that the SMS ensures these properties, the BAB protocol ensures its standard properties, and transaction execution is deterministic, we now show that the overall system can guarantee the conventional safety and liveness properties of BFT protocols regardless of the SMS implementation.
The BAB protocol ensures that the execution layer of all non-faulty nodes receives the same sequence of transactions.
Due to deterministic execution, the execution layer of all non-faulty nodes will translate transaction executions into the same sequence of \fetch and \bump calls, satisfying the SMS's assumptions.
Then, the availability of SMS ensures that all non-faulty nodes can advance to every state version (either by execution or by \forward), and at least $2f+1$ nodes
that advance a version have executed the corresponding transaction (rather than \forward-ed over it).
Combining these statements, for each version, at least $f+1$ non-faulty nodes have executed the corresponding transaction.
Finally, the correctness of the SMS ensures that as long as executions start from consistent pre-states, they yield consistent results and transition to consistent post-states.
Given that all nodes start from the same initial state, by induction, all non-faulty nodes will produce consistent results for all transactions they execute.
As a result, for each transaction, the client can collect $f+1$ identical responses from executing non-faulty nodes, satisfying the safety and liveness properties of BFT protocols.

\subsection{Challenges}

Ensuring availability is challenging.
If a state shard is stored exclusively on faulty nodes, the shard may be lost.
However, storing each shard on at least $f+1$ nodes to prevent this results in storage overhead that scales with the number of nodes, thereby undermining storage scalability.

Ensuring correctness is also challenging.
Since the system may contain up to $f$ faulty nodes, these nodes may respond to retrieval requests with incorrect or outdated data.
The node retrieving the state must be able to identify and discard such invalid data to prevent divergence in execution.
A straightforward approach is to collect $f+1$ identical responses from distinct nodes, ensuring at least one correct response.
However, this method requires storing each shard on at least $2f+1$ nodes, which again leads to storage overhead proportional to the number of nodes.

Last but not least, retrieving state shards from other nodes introduces additional network traffic and, more importantly, places retrieval on the critical path of execution.
While waiting for retrieval, execution is blocked, and the node cannot process other transactions because execution must remain sequential to ensure consistency.
This leads to increased latency and reduced throughput due to diminished node utilization.
