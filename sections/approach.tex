\section{A Decomposing Approach}
\label{sec:approach}

As previously discussed in \autoref{sec:bg}, implementing sharding in BFT protocols significantly impacts safety and liveness properties.
Next, we will decompose BFT protocols into consensus and execution layers and analyze the effects of sharding on each layer separately.

Sharding the consensus layer degrades the safety and liveness of the system.
It is theoretically impossible~\cite{bracha1985asynchronous} to tolerate $f$ Byzantine faults with less than $3f+1$ nodes without the help from synchronous network condition~\cite{zamani2018rapidchain}, trusted hardware~\cite{dang2019towards}, PoW puzzles~\cite{wang2019monoxide}, etc.
Thus, keeping the goal of achieving these properties in mind, we should avoid sharding the consensus layer.

Should we decompose the BFT protocols and solely shard the execution layer?
Regrettably, a sharded execution layer can still significantly impact both safety and liveness properties.
In BFT protocols, a client must await $f+1$ identical responses from distinct nodes before committing a transaction to tolerate up to $f$ Byzantine faults.
In sharded blockchains, a particular transaction is invariably executed by a limited set of nodes (thus achieving storage scalability), consequently limiting the number of Byzantine faults that can be tolerated.
Given a sufficient total number of nodes, the $\frac{1}{3}$ faulty nodes can overwhelm the committee and induce safety issues (\eg, sending identical incorrect responses) and liveness issues (\eg, non-responsiveness).

While neither the consensus layer nor the execution layer in its entirety is amenable to sharding, we can further decompose the execution layer and \emph{extract} the state, considering that storage scalability primarily concerns the storage occupied by the (replicated) state.
Fortunately, as long as all nodes continue to execute every transaction (and respond to the client), sharding the state will no longer compromise the safety property.
Interestingly, although a sharded state is unrelated to typical liveness issues addressed by standard BFT protocols (leader rotation, reply withholding, etc.), it can introduce a novel liveness concern if nodes cannot obtain the required state shards, leading to execution being blocked.
This implies that the liveness property now additionally hinges on the \emph{availability} of any shard of the state.
State availability is a non-issue for most BFT protocols, where the execution layer maintains all relevant states locally at the nodes.
However, when a sharded state is coupled with a non-sharded execution layer, the execution layer cannot process all transactions using only locally stored shards, and the liveness of execution depends on the accessibility of remote shards to the nodes.

We now present our approach, as illustrated in the bottom section of \autoref{fig:approach-compare}.
A state management system (SMS) is separated from the execution layer and serves as the dedicated state storage on the nodes.
While every transaction is executed by all nodes, the state shard(s) accessed during its execution are stored only on a subset of the nodes.
The SMS of the remaining nodes is responsible for loading the required shards on demand to facilitate local execution.
These loaded shards may be discarded after the transaction is executed, and the SMS will reload them upon the next access.

Ultimately, this decomposition design achieves a separation of concerns~\cite{reade1989elements}.
The global consensus and execution layers are responsible for ensuring safety and liveness, and any off-the-shelf Byzantine Atomic Broadcast (BAB) and BFT protocols~\cite{pbft,gueta2019sbft,yin2019hotstuff,danezis2022narwhal,spiegelman2022bullshark} can be adapted to fulfill the requirements of these layers.
Conversely, the SMS does not need to consider safety at all—it receives an ordered list of transactions guaranteed to be consistent across all correct nodes.
Its sole responsibility is to manage the state shards in a manner that satisfies storage scalability —- the overall storage consumption per shard depends only on the shard size, not the number of nodes —- and availability —- every state shard must be accessible to every node.
While this design space has rarely been explored (quoting a 2023 survey on sharding replication systems~\cite{solat2023sharding}: \emph{To the best of our knowledge, actually there is no protocol that uses storage sharding without processing sharding}), recent high-throughput BFT protocols~\cite{danezis2022narwhal,giridharan2024autobahn} adopt a similar approach, decoupling a delivery layer (reliable broadcast) from the consensus and execution layers and independently scaling it up to achieve optimal throughput.

\paragraph{Achieving Storage Scalability and Availability in BFT Settings.}
To achieve both storage scalability and availability, we must distribute the storage overhead (i.e., the \emph{redundancy}) of each shard and the responsibility for storing it across a sufficiently large set of nodes to tolerate $f$ failures among them, while maintaining a fixed amount of redundancy across all these nodes.
Drawing upon techniques from advanced distributed databases, we utilize erasure codes~\cite{ec} for this purpose, which are designed to mask a configurable number of failures within a fixed redundancy budget.
To tolerate $f$ failures, we can employ an EC$(k+2f,k)$ scheme, which generates $2f$ \emph{parity} shards for every $k$ original state shards\footnote{In this work, we consider systematic codes like Reed-Solomon (RS) codes~\cite{reed1960polynomial}.}, forming a shard \emph{stripe}. Any combination of $k$ state shards and parity shards can reconstruct the original $k$ state shards.
We then store the $k+2f$ shards of the stripe on $k+2f$ distinct nodes.
Any supermajority of $2f+1$ nodes will intersect this set of $k+2f$ nodes with at least $k+f$ nodes, of which at least $k$ must be correct, allowing the stripe to be reconstructed from the shards they store.
Concurrently, the redundancy remains fixed regardless of the total number of nodes, provided that $k$ is proportional to $f$.
We will revisit the application of erasure codes and the detailed redundancy analysis in \autoref{sec:overview}.

\paragraph{Analysis of Network Traffic Overhead.}
Initially, this decomposition approach might appear expensive concerning network traffic.
Nodes seemingly incur both additional bandwidth for continuously loading shards from each other and increased latency due to the necessity of on-demand loading before processing can commence.
However, in practice, it is more feasible than it initially appears.
As previously noted in the problem settings (\autoref{sec:bg}), most transactions are anticipated to access only a single or a small number of shards.
By configuring a small shard size (e.g., KB level), the network traffic can be maintained within a reasonable budget.
The latency associated with on-demand loading can be mitigated through speculative pushing (\autoref{sec:impl}).
Furthermore, real-world workloads are predominantly skewed~\cite{powerlaw}.
By simply caching a small proportion of shards (\autoref{sec:impl}), the total network traffic can be significantly reduced~\cite{fan2011small}.
A more detailed analysis is provided in \autoref{sec:eval}.

Despite this positive result, the availability of state is still challenging for designing the storage layer, which is summarized as the following C1-C3.

\paragraph{C1: Garbage collection strategy.}
The nodes should not only store the latest view of the shards but also some previous ones in case the other (slower) nodes still need them for processing.
However, the nodes also cannot store all historical views or the storage overhead would grow unbounded.
It is critical to employ \emph{checkpoints and garbage collection} which, must not progress only when all nodes participate the checkpoint (or the faulty nodes can impede the garbage collection), while also ensure that any (correct) node that did not participate the checkpoint can transfer the checkpoint view of the shards from \emph{some} other nodes, skip the processing until the checkpoint and be free from liveness issue.

\paragraph{C2: Constant redundancy.}
As stated in the problem settings (\autoref{sec:bg}), \sys can perfectly scale to any number of nodes and remain $O(state\ size)$ storage overhead \ie storing only constant redundancy of the state.
Storing constant number of verbatim copies of the shards can straightforwardly fulfill this requirement but destroy availability: with sufficient nodes, the faulty nodes will eventually overwhelm the storing nodes of a shard and cause state lost.
Deploying \emph{erasure code}~\xxx{cite} can effectively tolerate more faults while respecting the redundancy budget.
However, that leads to nontrivial design and safety reasoning, and also cause the next challenge.

\paragraph{C3: Mask encode and decode overhead.}
Compare to operating on verbatim copies, operating encoded stats add significant encode overhead: every shard update have to update the parities, costing computation and (what's more concerning) amplifying read.
At the same time, while systematic code \xxx{cite} can enjoy optimal read performance on happy path, faulty nodes can easily cause \emph{degraded read} by withholding the storing shards.
As the result, the design must ensure off-the-path encoding, and must avoid degraded read as much as possible.

Base on this observation, we propose a novel idea on the BFT scalability
\begin{quote}
    The BFT protocols should be decomposed into dedicated \emph{storage} and \emph{consensus} layers, each of whom should be scaling out in separate ways.
\end{quote}
As shown in \autoref{fig:approach-compare}, with decomposed storage and consensus layers, transaction processing is fully replicated to every node with a global consensus layer, while the state is sharded and partially stored on every node, managed by the storage layer.
To process a transaction, nodes must synchronize the shards accessed by the transaction but not stored locally ahead of the time.
These synchronized shards are only for supporting processing -- the nodes that are not obligated to store a shard (according to the storage layer) may discard it and synchronize it again from the obligated nodes later.
While this design space is rarely explored (quote a survey on sharding replication systems from 2023~\cite{solat2023sharding}: \emph{To the best of our knowledge, actually there is no protocol that uses storage sharding without processing sharding}), the idea is akin to the one behind recent high throughput BFT protocols~\cite{danezis2022narwhal,giridharan2024autobahn}, who decompose BFT protocols into delivery and consensus layers and independently scale the former one.

Essentially, the decomposition of architecture leads to the separation of concerns~\cite{reade1989elements}.
The storage and the consensus layers each take charge in different desirable properties: the safety is guaranteed by the consensus, the storage scalability is guaranteed by the storage, while the liveness is concerned by both of them, but in different aspects.
On one hand, consensus layer must progress on ordering the transactions to be processed, as the vanilla ``liveness'' definition in a typical BFT protocol.
On the other hand, storage layer must ensure the \emph{availability} of every individual state shard, or the processing cannot continue when some accessed shards are lost.
This new source of liveness violation (\ie failing on availability) is unique to our new scaling approach, and is the main focus of the design later in \autoref{sec:overview}.
\lijl{One way to structure this argument: consensus is to establish a total order of transactions. State storage is to support the execution layer. We are basically offloading state management in the execution layer to distributed storage.}

To summarize, what we have seen from previous works is that state sharding is always accomplished with processing sharding, while processing sharding leads to undesirable security guarantee.
This leads us to think about \emph{the separation of concern}~\xxx{cite} and come up with our approach:
\begin{quote}
    The processing layer and the storage layer of BFT protocols should be considered separately.
    The processing layer is responsible for \emph{consistency}, and should not be sharded to maximize the safety guarantee;
    the storage layer is only responsible for \emph{availability} and can employ arbitrarily sharding scheme just as in distributed databases.
\end{quote}
