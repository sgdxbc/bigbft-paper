In \autoref{sec:bg} we observe that, previous works attempt to scale out processing and storage at the same time and can only settle on the trade-offs among the three properties.
Meanwhile, recent works have made noticeable progress on just improve the processing scalability~\cite{gueta2019sbft,yin2019hotstuff,danezis2022narwhal,spiegelman2022bullshark}, reaching near optimal performance without sacrificing safety and liveness properties.
At the same time, distributed databases have always been perfectly scalable and supporting to tolerate configurable faults with erasure coding \xxx{cite} techniques.
Base on this observation, we propose a novel idea on the BFT scalability
\begin{quote}
    The BFT protocols should be decomposed into dedicated \emph{storage} layer and \emph{consensus} layer, and the layers should be scaling out in different ways.
\end{quote}
While this design space is rarely explored (quote a survey on sharding replication systems from 2023~\cite{solat2023sharding}: \emph{To the best of our knowledge, actually there is no protocol that uses storage sharding without processing sharding}), the idea is akin to the one behind recent high throughput BFT protocols~\cite{danezis2022narwhal,giridharan2024autobahn}, who decompose BFT protocols into delivery layer and consensus layer and independently scale the former one.

The decomposition of architecture leads to the separation of concerns~\cite{reade1989elements}.
The storage layer and the consensus layer each takes charges in different desirable properties: the safety is guaranteed by the consensus, the state scalability is guaranteed by the storage, while the liveness is concerned by both of them, in different aspects.
On one hand, consensus layer must progress on make decisions of the transactions to be processed, which is the same to the liveness in a typical BFT protocol.
On the other hand, storage layer must ensure the \emph{availability} of the state to support the nodes to process whatever transactions decided by the consensus.
This is a unique thing to this work and lead to several challenges, which we will discuss later.

\paragraph{Network overhead.}
At first glance this decomposition may be a costly approach that has to pay both extra bandwidth for nodes continuously synchronizing shards to each other and extra latency for ad-hoc synchronization.
In fact, it is more practical than it seems like.
As previously mentioned in the problem settings (\autoref{sec:bg}), most transactions are expected to access only single or few shards, so with sufficient number of shards, the amount of transferred data for processing one transaction will be acceptably small.
Also, even in fully replicated systems, there's still a baseline bandwidth occupation for dispersing the transactions and replying the clients, and additionally sending shards will not make bandwidth consumption dramatically worse.
The synchronization latency can be masked with speculation (\autoref{sec:impl}).
And last but not least, the real world workload are mostly skewed~\xxx{cite zipf}.
By simply caching a small fraction of shards (\autoref{sec:impl}), the total amount of transferred data can be greatly reduced.

Despite this positive result, the availability of state is still challenging for designing the storage layer, which is summarized as the following C1-C3.

\paragraph{C1: Garbage collection strategy.}
The nodes should not only store the latest view of the shards but also some previous ones in case the other (slower) nodes still need them for processing.
However, the nodes also cannot store all historical views or the storage overhead would grow unbounded.
It is critical to employ \emph{checkpoints and garbage collection} which, must not progress only when all nodes participate the checkpoint (or the faulty nodes can impede the garbage collection), while also ensure that any (correct) node that did not participate the checkpoint can transfer the checkpoint view of the shards from \emph{some} other nodes, skip the processing until the checkpoint and be free from liveness issue.

\paragraph{C2: Constant redundancy.}
As stated in the problem settings (\autoref{sec:bg}), \sys can perfectly scale to any number of nodes and remain $O(state\ size)$ storage overhead \ie storing only constant redundancy of the state.
Storing constant number of verbatim copies of the shards can straightforwardly fulfill this requirement but destroy availability: with sufficient nodes, the faulty nodes will eventually overwhelm the storing nodes of a shard and cause state lost.
Deploying \emph{erasure code}~\xxx{cite} can effectively tolerate more faults while respecting the redundancy budget.
However, that leads to nontrivial design and safety reasoning, and also cause the next challenge.

\paragraph{C3: Mask encode and decode overhead.}
Compare to operating on verbatim copies, operating encoded stats add significant encode overhead: every shard update have to update the parities, costing computation and (what's more concerning) amplifying read.
At the same time, while systematic code \xxx{cite} can enjoy optimal read performance on happy path, faulty nodes can easily cause \emph{degraded read} by withholding the storing shards.
As the result, the design must ensure off-the-path encoding, and must avoid degraded read as much as possible.
