Actually, sharding the consensus layer alone can substantially degrade the safety and liveness of the system.
It is theoretically impossible~\cite{bracha1985asynchronous} to tolerate $f$ Byzantine faults with less than $3f+1$ nodes without the help from synchronous network condition~\cite{zamani2018rapidchain}, trusted hardware~\cite{dang2019towards}, PoW puzzles~\cite{wang2019monoxide}, etc.
Thus, keeping the goal of achieving these properties in mind, we should avoid sharding the consensus layer.

Should we decompose the BFT protocols and solely shard the execution layer?
Regrettably, a sharded execution layer can still significantly impact both safety and liveness properties.
In BFT protocols, a client must await $f+1$ identical responses from distinct nodes before committing a transaction to tolerate up to $f$ Byzantine faults.
In sharded blockchains, a transaction is invariably executed by a limited set of nodes (thus achieving storage scalability), limiting the number of Byzantine faults that can be tolerated.
Given a sufficient number of nodes, the $\frac{1}{3}$ faulty nodes can overwhelm the committee and induce safety issues (\eg, sending identical incorrect responses) and liveness issues (\eg, non-responsiveness).

While neither the consensus layer nor the execution layer in its entirety is amenable to sharding, we can further decompose the execution layer and \emph{extract} the state, considering that storage scalability primarily concerns the storage occupied by the (replicated) state.
Fortunately, since all nodes continue to execute every transaction (and respond to the client), sharding the state will no longer compromise protocol safety.
However, the approach needs to ensure \emph{availability} of all the state shards;
otherwise, the execution layer can be blocked accessing some state, violating liveness.

\paragraph{Achieving Storage Scalability and Availability in BFT Settings.}
To achieve both storage scalability and availability, we must distribute the storage overhead (i.e., the \emph{redundancy}) of each shard and the responsibility for storing it across a sufficiently large set of nodes to tolerate $f$ failures among them, while maintaining a fixed amount of redundancy across all these nodes.
Drawing upon techniques from advanced distributed databases, we utilize erasure codes~\cite{ec} for this purpose, which are designed to mask a configurable number of failures within a fixed redundancy budget.
To tolerate $f$ failures, we can employ an EC$(k+2f,k)$ scheme, which generates $2f$ \emph{parity} shards for every $k$ original state shards\footnote{In this work, we consider systematic codes like Reed-Solomon (RS) codes~\cite{reed1960polynomial}.}, forming a shard \emph{stripe}.
Any combination of $k$ state shards and parity shards can reconstruct the original $k$ state shards.
We then store the $k+2f$ shards of the stripe on $k+2f$ distinct nodes.
Any supermajority of $2f+1$ nodes will intersect this set of $k+2f$ nodes with at least $k+f$ nodes, of which at least $k$ must be correct, allowing the stripe to be reconstructed from the shards they store.
% Concurrently, the redundancy remains fixed regardless of the total number of nodes, provided that $k$ is proportional to $f$.
Concurrently, as the number of nodes increases, we have the opportunity to increase $k$ accordingly through efficient \emph{transcoding}~\cite{maturana2020access,maturana2022convertible,maturana2023bandwidth,yao2021stripemerge}, increasing the stripe size while reducing the average per-shard storage consumption on each node through less parity shards, in order to achieve storage scalability.

Implementing an SMS is challenging despite its logical appeal.
While state sharding borrows from distributed databases, SMS operates in a fundamentally different environment and faces distinct constraints.
Specifically, SMS must support independent execution on every node, with each node making progress at a different rate.
Thus, SMS must concurrently manage multiple state versions and quickly identify discardable historical versions to avoid unbounded storage.
Erasure coding, while used, is computationally expensive and can degrade performance if not carefully employed.
Most importantly, the design must tolerate $f$ faulty nodes, necessitating quorum-based communication (often supermajority), and we must examine that the additional network traffic brought by them is acceptable.
In the following section, we present our design of \sys and demonstrate how it tackles these challenges.

As shown in \autoref{fig:approach-compare}, with decomposed storage and consensus layers, transaction processing is fully replicated to every node with a global consensus layer, while the state is sharded and partially stored on every node, managed by the storage layer.

Essentially, the decomposition of architecture leads to the separation of concerns~\cite{reade1989elements}.
The storage and the consensus layers each take charge in different desirable properties: the safety is guaranteed by the consensus, the storage scalability is guaranteed by the storage, while the liveness is concerned by both of them, but in different aspects.
